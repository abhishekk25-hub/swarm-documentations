1. Why Phase 2 Matters
Phase 2 is a significant step up in ambition, scope, and scrutiny compared to Phase 1. The client has reviewed every Phase 1 delivery in detail and provided specific, concrete requirements for what Phase 2 must do differently.


The core purpose of this benchmark has not changed: we are building training data that proves multi-agent AI systems outperform single-agent AI on tasks where coordination, parallelism, and structured decomposition are not optional — they are the only way the work gets done correctly. But Phase 1 revealed critical execution failures that undermined that purpose. Phase 2 must not repeat them.


What the client needs from Phase 2.2:


* Tasks that are genuinely difficult because of their scale, evidence burden, judgment, and coordination requirements.
* One standard package contract so the agent and verifier always use the same input and output locations.
* A readable tests/rubric_manifest.json that documents every scored check implemented in tests/verify.py.
* Rubrics that combine structural checks, reward-hacking checks, and trusted partial-oracle checks instead of rewarding file shape alone.
* Recent, less-canonical source material that requires the agent to read the supplied evidence rather than answer from pretraining memory.
* Fair SA and MA runs under the same instruction, environment, verifier, tools, and time budget. SA should score low for a genuine capability reason, while MA should improve but remain meaningfully challenged, with a minimum 18 percentage-point SA-to-MA gap.
* A faithful high_level_prompt.md, preserved separately from instruction.md, restating only the deliverables the requester actually asked for.
* Three execution modes for every task — single, multi, and multi_noplan — run against the same final package, so the value of the supplied decomposition.yaml itself is demonstrated, not assumed.


Every requirement in this document exists to make the reward measure the actual work. A polished file is not enough unless its values, evidence, coverage, and conclusions are also checked.


Every item in this document traces back to a concrete Phase 1,2 failure or a concrete client request. Read it before you write a single line.

2. Harness Setup — Why We Moved to OpenCode and How to Set Up Locally
2.1 Why We Left Kimi-CLI
Phase 1 used the Kimi-CLI harness. Phase 2 runs on the OpenCode harness (swarmbench-harness). The switch was not optional — Kimi-CLI had architectural ceilings that Phase 2’s requirements made impossible to work around:


* Maximum DAG depth of 1. Sub-agents in Kimi-CLI cannot spawn their own sub-agents — a hard-coded role guard blocks it. Phase 2 requires dag_depth ≥ 2.


* Default concurrency cap of 4 background agents. Reaching the 50+ sub-agent Hard tier would require a one-line config change in the harness that we do not own.


* Background agent trajectories are invisible. Background sub-agent steps are stored in a private session directory the harness never relays. If 50 parallel agents all run in the background, zero of their step-level trajectories appear in the ATIF output — making trajectory collection for training data impossible.


* 15-minute background agent timeout. Long writing and browsing tasks routinely exceed this and would be silently killed with no error surface.


OpenCode solves all of these. It supports genuine hierarchical nesting, scales to 50+ concurrent agents, and collects full ATIF-v1.6 trajectories for every sub-agent.


You can also understand OpenCode in detail from the document below:
MAS<>Turing - OpenCode-Analysis
2.2 Setting Up the Harness Locally
Every trainer must set up and run the harness locally before authoring a task. You cannot deliver a task without execution logs, and you cannot generate execution logs without the harness running.


Harness repository: https://github.com/MathavanSG14/swarmbench-harness


Phase 2 KT session (watch this first): https://drive.google.com/file/d/19f0vmRdY4IwYuAjIgXMyQD_G0dY5kGB0/view


The KT session walks through: cloning the harness, building the Docker environment, running a task in single-agent and multi-agent mode, and reading the output execution logs. Watch it in full before running your first task.


Minimum local setup steps:


1. Clone the harness: git clone https://github.com/MathavanSG14/swarmbench-harness


2. Install Docker and ensure it is running


3. Follow the harness README for API key configuration


4. Run the example task from the example_tasks/ directory to confirm your setup works


5. Confirm execution_logs/single-opencode-agent/ and execution_logs/multi-opencode-agent/ are generated with non-empty opencode.txt and trajectory.json files


Do not author a task before you have a working local harness run. The Quality Gate will reject any task whose execution logs are missing, hand-fabricated, or generated against a different version of the task than you are submitting.

Delivery now requires a third execution mode, multi_noplan — the same multi-agent swarm run WITHOUT decomposition.yaml injected, so the actual value of the supplied decomposition is demonstrated rather than assumed. multi_noplan is only available after a forced reinstall — a normal git pull is not enough, because pipx/pip can retain the old package version:


git clone https://github.com/MathavanSG14/swarmbench-harness.git
cd swarmbench-harness
git pull
cd mascloud_client

mascloud run <task_folder> --mode multi
mascloud run <task_folder> --mode multi_noplan


3. What Went Wrong in Phase 1 — Client Feedback and Rules Going Forward
The client reviewed Phase 1 deliveries in detail and rejected a significant number of tasks. Understanding these failures is mandatory — they are not edge cases. They are patterns that will repeat if you are not actively watching for them.


________________


3.1 AI Artifacts Left in Task Files
What happened: Several tasks were drafted with AI assistance but submitted without being read end-to-end. The result was leftover LLM comments in instruction.md, contradictions between instruction.md and decomposition.yaml, and reducer logic in decomposition.yaml that directly violated the task’s own counting rules — all of which the trainer would have caught with a single careful read.


Rule: Every file in your task package — instruction.md, decomposition.yaml, tests/judge.py, tests/verify.py — must be read end-to-end by the trainer before submission. AI tools can help you draft, but you are responsible for the final content. Any non-relevant comment, filler sentence, or contradiction between files is a trainer quality failure. AI should be used only as a friendly research tool not as a task generator.


________________


3.2 Trainers Not Verifying SA and MA Trajectories
What happened: Trainers submitted tasks without checking whether the SA and MA runs actually reflected genuine task attempts. The client’s QA team was the first to catch broken runs — this should have been caught internally.


Rule: Before submitting, open all three trajectory files (single, multi, multi_noplan) and check:


* SA run: Did it actually attempt the full task, or did it silently skip most of it? Does opencode.txt show real tool calls across the full scope of the task?


* MA run: Did sub-agents follow the decomposition? Did the reducer produce correct aggregated output, not inflated or contradictory results?


* multi_noplan run: Did it finish cleanly enough to produce usable logs? A crash or an unrecovered rate-limit failure is not acceptable evidence — multi_noplan has no target reward of its own, but it must actually complete.


* reward.json for single and multi: Is the gap ≥ 18 pp? This is now a hard final-validation gate, not just an internal sanity check (see §3.9). Does the gap come from the MA system doing genuinely more work, or from a spec misread, a broken verifier, or an engineered scoring advantage?


* Whether the gap was achieved due to a hallucinated LLM judge or Trainer created verifier fault, which does not resonate with the intent of the task.


* SA output vs. expected output: If using an LLM judge, read the SA output yourself and compare it to what the judge awarded. If the judge gave a low score for output that is actually reasonable, the rubric is broken — fix it before submitting.


The client’s QA is the second check. You are the first. Do not ship a task whose trajectories you have not personally reviewed.


________________


3.3 LLM Judge Giving Bad Rewards Due to Weak Rubrics
What happened: Phase 1 LLM judges were built with rubrics that were too vague, structurally biased, or easy to game. The same model that produced the agent’s output was often used to grade it — leading to hallucinated scores and self-lenient grading. Some rubrics were written to expect SA to fail before reading the output.


Rules: - Use any other models which are available in serverless of fireworks -


![][image1]


— never the same model family as the agent - Do not trust the judge score blindly. Read the agent’s output yourself. If the judge awarded 0.2 on output that is substantively correct, your rubric is the problem - Never write language in a judge prompt that names which agent type should win. The judge must evaluate output quality neutrally, with no reference to “single agent” or “multi agent” expected behavior - Rubric items must be grounded in the content of the agent’s output — not in how the task was coordinated


________________


3.4 Engineered Scoring Gaps — Hard Rejects
The client will permanently exclude any task where the SA vs MA gap is manufactured through verifier or judge mechanics rather than through genuine task difficulty. These patterns have each been found in submitted tasks and are all hard rejects:


Binary gates before the LLM judge runs A structural precheck that writes reward = 0.0 before the LLM judge sees the output is a manufactured gap. A 6-word shortfall in a summary or a minor file-path mismatch zeroing an otherwise complete submission is not a capability signal. No binary gates before substance scoring. Structural prechecks must either be soft/banded or folded into the additive rubric.


Step-band ceilings min(LLM_score, step_ceiling) where the ceiling changes by 27pp based on a single field value crossing a threshold is a cliff, not a signal. A one-field miss must produce a proportional deduction. All ceilings must be continuous and linear.


Score caps on SA min(score, X), cap = max(0.0, 1.0 - n * penalty), or any hard percentage ceiling on SA’s reward — regardless of how it is framed — artificially reduces SA reward and inflates the gap. No score caps are permitted anywhere in verifier or judge code. This is a hard reject.


Multiplicative penalty stacking When a single error triggers the penalty factor, summary factor, and multiplier simultaneously — producing a 33pp deduction from what is structurally a ~5pp error — it is an amplification artifact. All penalty dimensions must be additive and independent. No stacked multipliers on a single error source.


Coordination-pattern language in judge prompts Scoring rubrics must not name the coordination pattern (“fan-out with grep-verified evidence”, “single-pass agent”). The judge must apply the same rubric to both SA and MA output. Naming expected coordination methods biases the judge toward MA and is grounds for rejection.


Static checks blocking the LLM judge No task may mix deterministic static checks (exact key matching, regex word counts, file-path existence) with an LLM judge in a way where a static failure prevents the LLM from running at all. The LLM judge must see the full submission. Static gates that prevent the judge from running are not acceptable.


Reward file edited manually Directly editing reward.json or test-stdout.txt to a value inconsistent with what the verifier’s own per-check output produces is fraud. Tasks with edited reward files are permanently excluded.


Drop the complex scoring systems and keep it simple — one point per check, that's it. For example, if a step is done correctly, it gets one point. No tiers, no weightage, no step counts. From now on, any task with an artificial or weighted reward structure will be rejected, no matter what was said in instruction.md, and both agents were aware of it. This still holds exactly as written — §3.9 adds a required reporting contract on top (named component fields, a required check-count composition) using the same equal, additive combination described there. It does not reintroduce per-check weighting.


________________


3.5 Verifier and Rubric Design Rules
The gap must come from the task's genuine difficulty, not from the way the verifier awards points. These rules apply to every Phase 2.2 task:


* Use one standard grader: tests/verify.py. tests/test.sh must invoke /tests/verify.py, and the verifier must write the final reward to /logs/verifier/reward.txt. Do not use judge.py, verifier.py, or another verifier-named script at the root of tests/.


* Document every scored check in tests/rubric_manifest.json. The manifest is the client-readable rubric. It must describe the complete set of checks registered in verify.py, not only a selected subset.


* Use all three required check categories. Every manifest must contain at least one static_checks_<n>, one reward_hacking_checks_<n>, and one partial_oracle_checks_<n> entry. Number each category sequentially from 1 without gaps.


* Use exactly five fields for every manifest entry. Each entry must contain detailed_explanation_of_checks, weight, agent_output_path, check_function, and how_it_prevents_task_authenticity_violation. Do not add extra fields.


* One point per check, additive, no weightage. Every manifest entry declares weight: 1. Score the task as checks passed divided by total checks. Do not use multipliers, category floors, score caps, or step-based ceilings.


* Keep the manifest and verifier in one-to-one alignment. total_checks must equal the number of manifest entries and the number of checks registered by verify.py. Every check_function must resolve to real implementation logic in verify.py or an allowed helper under tests/test_logic/.


* Use exact output paths. agent_output_path may be one path or a list for a check that covers several artifacts. Every declared path must begin with /logs/agent/. The identical paths must appear in instruction.md and be opened directly by verify.py. The verifier must never search arbitrary folders for an output.


* Use deterministic code for exact facts. File existence, schemas, identifiers, row counts, arithmetic, uniqueness, and fixed invariants should be checked in code.


* Use an LLM only for genuinely qualitative checks. verify.py may call an independent LLM for faithfulness, synthesis, relevance, or visual meaning. A separate judge.py file is not required or permitted under the standard naming convention.


* Use partial oracles where trusted facts can be verified. A full answer key is not required, but selected stable values should be manually verified and stored as grader-only test data. Where a human can verify an image or video, add a partial-oracle or content check for that artifact as well.


* Do not let structure outweigh substance. Structural checks confirm that an artifact can be consumed. Reward-hacking and partial-oracle checks must confirm that the work inside it is authentic, grounded, and consistent.


* Preserve partial credit. Each check should be independently scoreable. A partially correct submission should receive proportional credit instead of being reduced to zero by one unrelated formatting failure.


* Keep SA and MA conditions identical. Both modes receive the same instruction.md, environment, verifier, tools, and time budget. decomposition.yaml may add coordination structure but must not contain answer values or verifier hints.

3.6 Task Scope and Diversity
* No scriptable tasks. If a single correctly-written script can score ≥ 0.8 in under 30 minutes of effort, the task is not a benchmark task. It must require reasoning, synthesis, and judgment across sources.


Avoid tasks answerable from pretraining knowledge. Prefer recent, less-canonical books, presentations, reports, and datasets. Avoid classic textbooks, famous case studies, or widely circulated material that a base model may already reproduce from memory.


* Require the supplied evidence. The instruction and verifier should make the agent use the provided or cited source material. A strong answer produced without opening the task's sources indicates that the scenario or rubric is too dependent on parametric knowledge.


* Keep MA challenged as well. The client's current calibration direction is a low SA reward and an MA reward around 20-30% at most, rather than a near-perfect MA result. Treat this as the task-design target for now; the final automated acceptance threshold is still being reconciled and will be communicated separately.


* No unsolvable browsing tasks. Before building a browsing task, verify that every required URL is fetchable. If a site requires JavaScript rendering, pre-render and ship the content as input_artifacts/. Never deliver a task where the mandatory data is unreachable at runtime.


Ask a question to yourself once execution logs are obtained, whether the score and gap I have achieved are correct or not, which pushes you to more debugging and also reduces the failures from client rejection.

3.7 LLM Judge Call Reliability — Sandbox Constraints and Crash Fallback
What happened: Two separate, real issues surfaced while a reference verifier was reviewed by trainers: (1) a verifier can crash before it ever writes reward.json, leaving /logs/verifier/ completely empty with nothing but a non-zero exit code to explain why; (2) an earlier judge-calling pattern configured the model name, an alternate judge URL, and an alternate judge API key by reading environment variables the trainer was expected to "set before running" — but the verifier runs inside a Daytona sandbox that does not persist or accept an externally-injected environment variable, so those lookups always silently read None and fell through, looking configurable while never actually being configurable.


Rules:


* tests/test.sh must never let a verifier crash produce an empty /logs/verifier/. After verify.py runs, check whether reward.json exists. If it does not, write a fallback reward.json with all four required keys at 0.0, write a short error note to judge_justification.txt explaining that this was an infrastructure crash and not a scored zero, and preserve the non-zero exit status so the failure stays visible instead of vanishing.
* Never send an unbounded chain-of-thought to a reasoning model without disabling it. Reasoning ("thinking") models can silently spend an entire token budget on hidden reasoning and return content: null with finish_reason: "length", producing exactly the same "no/partial judge call" failure as an infrastructure error. Every judge request must send "chat_template_kwargs": {"enable_thinking": false}.
* Do not cap max_tokens on a judge call without a specific, tested reason. max_tokens is not a required field on a chat-completions call. A low or arbitrary cap risks the provider stopping generation before the model has actually reached a verdict, corrupting the JSON output the same way a real infrastructure failure would. Omit it unless you have verified a specific check needs a cap.
* Only auto-detect WANDB_API_KEY from the environment. Do not guess at other providers' usual env var names (OPENROUTER_API_KEY, FIREWORKS_API_KEY, OPENAI_API_KEY, etc.) — this is a real, demonstrated risk: an unrelated ambient key left over from something else in the sandbox can be silently picked up and tried for a provider nobody intended to use.
* Configure the judge model (and any alternate endpoint/key you genuinely need) as a static value in verify.py, not an environment variable. If the value needs to change per task, hardcode it directly in the file and have the trainer edit it there. An os.environ.get(...) lookup for anything beyond WANDB_API_KEY will not take effect in this sandbox.


A reference implementation of this plumbing — judge calling, redaction of any provider error text that leaks a masked API key, the test.sh crash-fallback above, and a backward-scanning JSON parser that survives a reasoning model's <think> block — is available as the SwarmBench Verifier Template: https://turing-company.slack.com/files/U09DRBN57L7/F0BNZKVQE87/swarmbench_verifier_template.zip.



Copy the plumbing only. The template's example CHECK_WEIGHTS (1, 1, 1, 2, 3, 1) and its (static*1 + reward_hacking*2 + partial_oracle*3) / 6 reward formula exist to illustrate the three-category check taxonomy for a generic audience — they are not Phase 2.2-compliant and must not be copied into a submitted task. Every check in a real Phase 2.2 rubric_manifest.json still declares weight: 1, additive, per §3.4 and §3.5. Use the formula in §3.9 for the final score, not this template's 1:2:3 weighting. Bring over the judge-calling and crash-fallback pattern; leave the weighting behind.

3.8 High-Level Prompt Requirement
What happened: Trainers wrote instruction.md as the only user-facing artifact, mixing the requester's actual ask together with methodology, worker assignments, tool guidance, and verifier logic. The client needs a short, faithful restatement of just the request — separate from the operational detail — and it must not be silently regenerated or overwritten by tooling.


Rule: Every task requires a high_level_prompt.md at the task root, in addition to instruction.md:


* Length: target approximately 250 words. Flag it if it falls under ~100 words or over ~450 words, and record the actual word count.
* Voice: write it as a direct, terse request from a busy requester in first person — the same voice as the §5 POC examples ("I work at the Treasury Board...").
* Content: state only what needs to be completed and which deliverables are required.
* Exclude: persona/company background beyond what's needed to frame the request, motivation or rationale, step ordering, methodology, tool guidance, worker assignments, verifier logic, score targets, or decomposition details. Those belong in instruction.md or decomposition.yaml.
* Independent restatement: do not copy section headers or paragraphs from instruction.md — it must be a genuinely shorter, independent restatement, not an excerpt.
* Consistent deliverables: every deliverable named in high_level_prompt.md must also exist in instruction.md, and it must not omit any major deliverable instruction.md requires.


instruction.md can still specify legitimate output paths, artifact schemas, and acceptance requirements — the decomposition remains the coordination artifact and should not leak into high_level_prompt.md.

3.9 Reward Component Contract and Content-Weighted Scoring
What happened: The client requires standardized category-level scoring, a minimum 60% content-check composition, and a minimum SA→MA gap enforced as a final-validation gate. This section defines the required implementation without changing the existing hard-reject rules in §3.4/§3.5.
Rule — reward.json component fields. reward.json must include the four required keys defined in §3.5:
* reward
* total_static_check_score
* total_reward_hacking_check_score
* total_partial_oracle_check_score
The three total_* fields must contain the mean score for their respective check categories. The reward field must contain the final normalized score.
Rule — standardized weighted scoring. First, calculate the mean score for each check category:
static_mean = mean of all static check scores
reward_hacking_mean = mean of all reward-hacking check scores
partial_oracle_mean = mean of all partial-oracle check scores
Then apply the required category weights:
reward =
(
    static_mean × 1
    + reward_hacking_mean × 2
    + partial_oracle_mean × 3
) / 6
The denominator must be 6, which is the sum of the category weights: 1 + 2 + 3. This keeps the final reward normalized between 0 and 1.
All checks within a category are averaged equally. The 1:2:3 weighting is applied only when combining the three category means. Do not use a simple /3 average, multiplicative penalty formula, clamp, or step ceiling.
Rule — manifest weights must match the verifier. rubric_manifest.json must accurately reflect the weights applied by verify.py. The required category weights are:
static_checks = 1
reward_hacking_checks = 2
partial_oracle_checks = 3
Any change to the verifier must also be reflected in rubric_manifest.json. The manifest must not declare all checks with weight: 1 if the verifier applies category-level weights of 1:2:3.
Rule — minimum 60% content-check composition. Content-based checks consist of:
* reward_hacking_checks
* partial_oracle_checks
At least 60% of all checks by count must be content checks, and no more than 40% may be structural checks. This composition requirement is separate from the 1:2:3 scoring formula and must be satisfied in addition to it.
content_check_count =
reward_hacking_check_count + partial_oracle_check_count


content_check_fraction =
content_check_count /
(structural_check_count + content_check_count)
The content check fraction must be at least 0.6.
Tasks should include at least three to five task-specific content rubrics. Minimum partial-oracle check requirement: Every task must contain at least six partial-oracle checks. Any task with fewer than six partial-oracle checks must be rejected and is not valid for submission. This requirement is independent of the 60% minimum content-check composition rule.
The 1:2:3 formula gives the two content categories a combined category weight of 5/6, while the structural category receives 1/6. Do not replace this weighted formula with an equal average.
Rule — minimum 18pp gap is a hard final-validation gate. Before submission, confirm that the final single and multi runs, using the same package, environment, verifier, and time budget, show a minimum 18 percentage-point gap. This is a submission-blocking requirement, not only an internal check described in §3.2.

4. What the Client Requires for Phase 2
These are the concrete requests from the client (CR-01 through CR-08, CR-13, CR-14 — the numbering has gaps from earlier internal-only items). Read each one — they directly define what you must build.
CR-01 — Browsing Tasks
Build tasks where sub-agents fetch live data from external databases. Example: given 70 WHO rare disease names, retrieve the top 3 active clinical trials from ClinicalTrials.gov, EU CTR, and China CTR for each.


How to implement: Use FetchURL for plain-text APIs and Shell(curl) for JSON REST APIs. Pre-verify every URL before building the task. If a site requires JavaScript, pre-render and ship the HTML as input_artifacts/. Add browsing to secondary_classification in task.toml.
CR-02 — Long Writing Tasks (100K+ Token Output)
Build tasks that require producing very long, structured documents — technical reports, systematic reviews, policy briefs — where the output itself exceeds 100,000 tokens.


How to implement: The agent must write sections in chunks using WriteFile with append mode, since the 131K context window cannot hold the full output in one generation. Design the task so sub-agents each produce a section (5K–10K tokens), and the synthesizer agent assembles them. Add long_writing to secondary_classification.
CR-03 — Creative Visualization Tasks
Build tasks where the output is a structured visual artifact: an HTML slide deck (Reveal.js), an SVG diagram, or a matplotlib figure generated via Shell execution.


How to implement: HTML and SVG are plain text — agents write them with WriteFile. For PNG output from matplotlib, the Dockerfile must install matplotlib. No native image generation tool exists; all visuals must go through code execution. Add multi_modal to secondary_classification.
CR-04 — Specialist and Hierarchical Coordination Patterns
Cover the specialist-routing and hierarchical coordination patterns. These are entirely absent from Phase 1. Specialist routing means different sub-agents handle different skill domains (one agent for data extraction, one for legal analysis, one for technical writing). Hierarchical means sub-tasks have clear dependency chains where output from one level feeds the next.


The OpenCode harness fully supports both patterns. Specialist routing is implemented by giving each sub-agent a scoped role in decomposition.yaml (e.g., one legal specialist, one federal-grants specialist, one cross-jurisdiction comparator). Hierarchical coordination is implemented by building explicit depends_on chains in the decomposition so one tier of sub-agents consumes the output of a prior tier.
CR-05 — Hierarchical Tasks
Take two existing fan-out tasks that share identical input data and merge them into a single hierarchical task with two parallel synthesis branches. The orchestrator fans out to readers, then routes reader outputs to two independent synthesizers working in parallel.
CR-06 — Hard Difficulty Tier (50+ Sub-Agents)
Push SWE and data-analysis tasks into the Hard tier. Hard means ≥ 20 parallel sub-agents at the widest level (dag_width ≥ 20). Phase 1 tasks clustered almost entirely at Medium (4–10 sub-agents). The OpenCode harness handles this natively — no manual concurrency cap config needed. Set dag_width accordingly in task.toml.
CR-07 — DAG Depth ≥ 2
Every Phase 2 task must have a minimum DAG depth of 2. This means at least one sub-agent whose result is consumed by another sub-agent before reaching the final synthesizer. Flat fan-out where all sub-agents feed directly to a single synthesizer is dag_depth = 1 and is no longer accepted.


Quality Gate enforcement: task.toml must declare dag_depth = 2 or higher. The QG static check will reject any task with dag_depth < 2.
CR-08 - Standard Rubric Manifest and Partial-Oracle Scoring
Every task must include tests/rubric_manifest.json. This fixed file tells the client what is being scored, which output each check reads, and where the implementing verifier logic lives.


The manifest must contain three categories:


1. static_checks_<n> - validates required files, schemas, coverage, and other deterministic package requirements.
2. reward_hacking_checks_<n> - detects duplicated coverage, placeholders, fabricated summaries, hollow visuals, and other shortcuts that can look complete without doing the task.
3. partial_oracle_checks_<n> - compares selected outputs with trusted, manually verified facts when a complete oracle is impractical.


Each check is worth one point and contains:


* detailed_explanation_of_checks
* weight: 1
* agent_output_path, containing one path or a list of paths, all beginning with /logs/agent/
* check_function
* how_it_prevents_task_authenticity_violation


The manifest must be a complete mirror of tests/verify.py: every documented check must exist in code, every scored verifier check must appear in the manifest, and total_checks must match both sides.


Rubrics must evaluate the actual task outcome. File presence and formatting may be checked, but they cannot create a meaningful reward floor without correctness, evidence, consistency, reward-hacking, and partial-oracle checks on top.
CR-13 — Scale Target per Category
The Phase 2 target is 50 tasks per new category (browsing, long writing, creative visualization, hierarchical). The current phase is a pilot — 1–2 tasks per category establish the template. Scale follows after the client approves the pilot samples.
CR-14 — Three Required Execution Modes
Every task delivery requires three fresh execution-log packages against the same final package, environment, verifier, and time budget: single, multi, and multi_noplan.


How to implement: Reinstall the harness per §2.3 so mascloud run --help lists all three modes, then run mascloud run <task_folder> --mode single, --mode multi, and --mode multi_noplan in sequence. multi_noplan runs the same multi-agent swarm without decomposition.yaml injected, demonstrating that the supplied decomposition is materially useful rather than decorative. It has no target reward or gap of its own, but an unrecovered crash or rate-limit failure is not acceptable evidence — it must finish cleanly. The resulting folder is named multi-opencode-agent-noplan/ under execution_logs/, matching the structure of the other two modes exactly (see §6.5).

5. How to Be Creative — Lessons from the POC Tasks
Phase 2 is explicitly process-based scoring. The verifier is not checking whether the agent matched a gold answer. It is checking whether the agent executed a credible professional workflow — with the right coverage, structure, and depth. This changes what makes a good task fundamentally.


Phase 2.2 note: The POC examples below remain useful for scenario design, decomposition, and deliverable creativity. Some of their original source choices and verifier descriptions predate the Phase 2.2 rubric standard and must not be copied as current verifier templates. New tasks must follow tests/rubric_manifest.json, tests/verify.py, /logs/agent/ output paths, partial-oracle checks, and the source-novelty requirement described in this document.


The four pilot POC tasks below were designed by trainers who thought like professionals first and task designers second. Study how they got there. Then go further.


________________


5.1 The Government Compliance Audit (Pipeline / Browsing)
The scenario: A policy analyst at the Treasury Board of Canada Secretariat is preparing a compliance presentation for senior management. She needs to audit every public repository under github.com/canada-ca against five GC Digital Standards: bilingual README, open licence, security policy, contributing guide, and last commit within 365 days.


What the trainer did: Started from a real job — a government analyst who would actually face this problem. The 74 public repos are real. The five digital standards are a real published policy framework. The deliverables (compliance spreadsheet, four presentation charts, a briefing note) are exactly what that analyst would bring to the meeting.


Why multi-agent wins: Each repo requires 8–12 separate page fetches (README, SECURITY.md, CONTRIBUTING.md, LICENSE, 2–4 workflow YAML files, issues tab, releases page) followed by qualitative assessment at each step. Across 74 repos that is 600–900 fetches. A single agent saturates its context after 10–12 repos and starts copying assessments from earlier repos or hallucinating fields it never fetched. Multi-agent assigns batches of 10–11 repos per worker — each with a clean context — and a reducer merges the seven batches and generates the four charts in Python.


What makes the verifier work without oracle: The verifier checks that compliance_matrix.csv exists with the right columns, that each of the four chart PNGs was generated, and that output.json has all required fields with no nulls. It does not compare values to a gold answer — any honest run against the real GitHub org will produce a correct result. Fabricated values fail because they do not match what the actual repo pages contain.


The lesson: Pick a real professional persona facing a real, publicly scoped dataset. The compliance standard already exists — you just need a real analyst role to frame the need. The task’s difficulty comes from the sheer breadth of pages to read, not from obscurity.

5.2 The Economics Textbook Study Guide (Hierarchical / Long Writing)
The scenario: A student has a 995-page introductory economics textbook (Principles of Economics, 34 chapters). They need a thorough prose summary of every chapter — a ~100-page Word document — so they can study the whole book efficiently without re-reading it.


What the trainer did: Found a real open-access textbook (OpenStax Principles of Economics 3e, 34 chapters, CC BY-SA). The deliverable is a single .docx file, not a JSON object. Each chapter requires several pages of “flowing prose that genuinely explains the chapter” — not bullet points, not a list of key terms, but real explanatory writing that teaches each chapter’s models and intuitions in order.


Why multi-agent wins structurally: A single agent reads the front of the book and writes strong sections for chapters 1–5, then degrades under the combined read+write load: it skips chapters, writes thin sections that miss specific models, blurs distinct chapters together, and stops well before chapter 34. The hierarchical design assigns one writer sub-agent per chapter (each reads ONLY its chapter and produces a 1,200–1,800 word faithful prose summary) and one assembler sub-agent that stitches all 34 sections into one cohesive study guide with proper headings.


Why the verifier works without oracle: The judge receives each chapter’s text from the PDF and each chapter’s written section from the .docx. It evaluates independently: does this section define the chapter’s key terms, explain the core models, walk the sections in order, and stay faithful to the book without fabricating content? 34 independent chapter grades, averaged. The judge cannot be gamed by writing a single generic “economics chapter” boilerplate — it cross-checks against the actual chapter.


The lesson: Long writing tasks make multi-agent shine because each chapter/section can get a fresh context budget. The deliverable format matters — a .docx is a more natural output for a study guide than a JSON blob, and the judge adapts to evaluate it. Use real published books or policy documents as input; they are pre-validated and publicly available.


Phase 2.2 source update: Use this example for its chapter-level hierarchical decomposition, not for its choice of a well-known introductory textbook. New tasks should use a recent, less-canonical book, report, or presentation that the base model is unlikely to have memorized, and the verifier must ground its checks in the supplied source.

5.3 The Emergency Procurement Audit (Specialist-Routing / Knowledge-Research)
The scenario: A lead procurement auditor for a multi-county oversight board is running a compliance sweep of 120 county emergency purchases across 12 purchase families (debris removal, IT recovery, medical supplies, etc.), 5 event types (storm, flood, wildfire, etc.), and 10+ states. The task is governed by binding rules in /input_artifacts/ (an audit rulebook with 20 rules, a research topic checklist with 17 topics, a report style guide, and a board presentation spec). The deliverable is a 13-worksheet Excel workbook.


What the trainer did: Built the scenario around a real government context (county emergency procurement under 2 CFR Part 200, FEMA rules, state bid thresholds). The binding input artifacts are not arbitrary — they replicate the actual rule structure a government auditor works under. The 13 worksheets are each a named deliverable a real oversight board would use: audit_trail, exception_sufficiency_ledger, frozen_citation_packet, vendor_identity_register, cross_jurisdiction_matrix, topic_coverage_matrix, etc.


Why specialist routing is the right pattern: The work has naturally distinct specialist roles that share no context: twelve purchase-family auditors (one per family), a federal Uniform-Guidance canon specialist, a FEMA procurement specialist, three regional state-law specialists, a vendor-identity/SAM.gov specialist, a topic-coverage research lead, a written-report writer, a board-presentation builder, and a reducer assembling the 13-sheet workbook. No single agent can hold 120 purchase packets across two conflicting legal regimes, 17 research topics, vendor reconciliation, AND produce a conformant written report.


Why the verifier works without oracle: The verifier checks the Excel workbook deterministically: are all 13 worksheets present? Does audit_trail have exactly 120 rows? Do all exception_sufficiency values start with sufficient/insufficient/unsupported? Does topic_coverage_matrix have rows for T01–T17 with findings ≥ 40 characters? Does summary have the correct metric names? None of these checks need a gold answer — they check structural completeness and format compliance that any honest run against real government data will satisfy.


The lesson: Specialist routing tasks shine when you can identify 5–10 genuinely non-overlapping expert roles that any professional organization would staff separately. Government compliance workflows are ideal because the rule structure is real, the roles are well-defined, and the deliverables are documented. Build the input artifacts (rulebook, topic checklist, style guide) yourself — they anchor the task to a real professional framework.

5.4 The Community Video Digest (Hierarchical / Data-Analysis + Multi-Modal)
The scenario: A community moderation data scientist on a Q&A network needs two things from a frozen snapshot of ~893 questions from 16 sub-forums: (1) the questions grouped into duplicate clusters (based on whether a single answer would serve both), and (2) a short 7–9 second animated MP4 video per sub-forum that the moderation team can drop into their weekly review.


What the trainer did: Used the real Stack Exchange Data Dump (CC BY-SA 4.0) — real moderator duplicate decisions, not synthetic labels. The 16 sub-forums are real (anime, astronomy, chess, cooking, etc.). Hard positives share almost no surface vocabulary (“my brakes squeal when wet” and “why do my brakes screech every time it rains?” are duplicates — same underlying question, different phrasing). Hard negatives look alike but need different answers (“adjust front derailleur” vs “adjust rear derailleur” are distinct). The videos are the deliverable the team actually watches — not a JSON artifact, but files they open.


The multi-modal design: Each sub-forum gets a worker who reads ~56 questions carefully, makes pairwise duplicate judgments, then renders one animated digest video using matplotlib + ffmpeg. The video shows the sub-forum name and the duplicate cluster count animating on screen. The verifier uses ffprobe to check duration (7–9 seconds), genuine frame-to-frame motion (not a static image), and validates that the cluster count in video_manifest.json matches the clusters actually formed in output.json.


Why the verifier works without oracle: Grouping quality is scored by deterministic pairwise F1 against the real moderator decisions — no model involved. Video quality is scored structurally by ffprobe. An agent that dumps all questions into one cluster gets near-zero precision. An agent that calls everything a singleton gets zero recall. The scoring is adversarial in both directions.


The lesson: Multi-modal deliverables (videos, charts, Word documents) are more credible training data than JSON-only tasks. They force the agent to actually execute a professional workflow that produces something a human would use. Use real datasets with real ground truth where possible — Stack Exchange, government portals, open-access textbooks, public GitHub organizations. The authenticity of the data is what makes the benchmark valid.

5.5 The Pattern Across All Four Tasks
Read these four tasks again and notice what they have in common:


1. A real professional speaks in first person. “I work at the Treasury Board.” “I’ve got an intro economics textbook.” “You are the lead procurement auditor.” The task is framed as a real job, not an abstract test.


2. The scale is quantified and justified. 74 repos × 8–12 fetches. 995 pages × 34 chapters. 120 purchases × 15 audit dimensions. The why_multi_agent field is not “it’s complex” — it is a specific breakdown that names where a single agent’s context runs out.


3. The deliverable is diverse and professional. A compliance spreadsheet + four PNG charts + a briefing JSON. A .docx Word document. A 13-worksheet Excel workbook. Sixteen .mp4 video files. None of these are “write an output.json with these keys.” They are deliverables real professionals actually produce.


4. The verifier checks completion, structure, and grounding — not style. Does the CSV have the right columns? Does the Word doc have all 34 chapter headings? Does the Excel workbook have 120 rows in audit_trail? Are the videos genuinely animated and the right duration? These checks are hard to fake without doing the work.


5. No single task is solvable by a script or a single database lookup. Every task requires reading, reasoning, judgment, and structured synthesis across many sources. The procurement auditor cannot just query SAM.gov — they have to classify exception sufficiency, check date consistency, identify federal flowdowns, and write a board presentation.


Push yourself to find this same quality in your own tasks. Start with a real professional role in a domain you know. Identify the part of their job that is too large for one person to hold in their head at once. Think about how that specific persona will use Claude, Antigravity, Codex, or any sort of multi-agent platform. Build the input artifacts from real sources. Design the deliverable to be something that a professional would actually send to a colleague, manager, friends or professor. Then build a verifier that checks whether the deliverable is complete and grounded — not whether it matched a gold answer you wrote.

5.6 Building a Robust Phase 2.2 Rubric
Start from the real failure modes of the task, then represent each one as an implemented check in tests/rubric_manifest.json and tests/verify.py.


* Static checks prove usability, not correctness. Confirm required files, schemas, identifiers, row counts, and output readability, but do not let those checks dominate the reward.


* Reward-hacking checks prove the work is authentic. Detect duplicated rows, repeated boilerplate, placeholder values, summaries that disagree with their source artifact, visuals that have the right filename but the wrong content, and suspicious cross-row uniformity.


* Partial-oracle checks prove selected values against trusted facts. Manually verify a representative sample of stable values and compare the agent's output with that sample. The objective is not to pre-author the full answer; it is to make fabricated but plausible-looking output lose credit.


* Every rewarded artifact needs a content check. A workbook, report, chart, image, or video should not earn substantive credit merely because it exists. Check whether it communicates or contains the requested result.


* Use exact paths throughout. The output path in instruction.md, agent_output_path in the manifest, and the path opened by verify.py must be identical and begin with /logs/agent/.


* Use deterministic checks whenever possible. Counts, joins, uniqueness, schemas, arithmetic, exact identifiers, and stable sampled values belong in executable logic.


* Use an independent LLM only when meaning requires it. LLM checks should evaluate source faithfulness, synthesis, relevance, or qualitative visual content. They must remain neutral about whether SA or MA produced the output.


* Keep every point equal. Each check declares weight: 1. Improve rubric quality by covering the real work with better checks, not by assigning large weights to selected categories.


Before running SA and MA, verify that the manifest parses, all three categories are present, every function reference resolves, and total_checks matches the verifier's registered checks.


Use this shape as the minimum pattern. The descriptions and functions must be written for the actual task rather than copied unchanged:

7. Common Mistakes Checklist
Before submitting, check every item on this list:
Instruction
* Every requested output uses an exact /logs/agent/... path.
* The same output paths appear in tests/rubric_manifest.json and tests/verify.py.
* Every packaged input is referenced using its /input_artifacts/... path.
* Every input referenced by the instruction exists under environment/input_artifacts/.
* The instruction contains no oracle values, scoring thresholds, verifier hints, or coordination-based scoring language.
* Examples use placeholders rather than real answer values.
* No required artifact is left at an unspecified or arbitrary location.
High-Level Prompt
* high_level_prompt.md exists at the task root, separate from instruction.md.
* Targets ~250 words; word count recorded and outside ~100–450 is flagged.
* Written in first person as a terse, deliverable-only request — no methodology, worker assignments, tool guidance, verifier logic, or score targets.
* Not copied from instruction.md section headers or paragraphs.
* Every deliverable it names also exists in instruction.md, with none of instruction.md's major deliverables omitted.
Decomposition
* dag_depth ≥ 2 — at least one sub-task depends on another sub-task with a downstream dependent


* Sub-task count matches estimated_sub_agents in task.toml


* No sub-task description references /tests/ paths


* No sub-task description contains oracle values or answer key content


* depends_on references all resolve to valid sub-task IDs


* No circular dependencies
Verifier and Rubric Manifest
* tests/rubric_manifest.json exists and contains static, reward-hacking, and partial-oracle checks.
* Every check contains the five required fields and declares weight: 1.
* Category numbering begins at 1 and contains no gaps.
* total_checks matches both the manifest entry count and the verify.py check registry.
* Every check_function resolves to implemented logic.
* Every path declared through agent_output_path begins with /logs/agent/ and matches instruction.md.
* The standard grader is tests/verify.py; no judge.py or verifier.py exists at tests/ root.
* Score equals checks passed divided by total checks, clamped to [0.0, 1.0].
* No category floors, score caps, multipliers, step ceilings, or agent-type-specific logic are present.
* Exact facts use deterministic checks; an independent LLM is used only for qualitative meaning.
* Every rewarded artifact has a content check, not only a presence or format check.
* Partial-oracle data is grader-only and does not leak answer values into the agent environment.
* tests/test.sh writes a zero-valued reward.json fallback and preserves a non-zero exit code if verify.py crashes before writing one (§3.7).
* Any LLM judge call configures its model as a static value in verify.py, not an environment variable, and does not send an unbounded max_tokens cap (§3.7).
* reward.json also exposes static_checks, reward_hacking_checks, partial_oracle_checks, and final_score, alongside the original four keys (§3.9).
* final_score is the equal average of the three category scores — (total_static_check_score + total_reward_hacking_check_score + total_partial_oracle_check_score) / 3 — with no per-category weighting (§3.9).
* content_check_fraction is ≥ 0.6 — at least 60% of all checks by count are reward_hacking_checks/partial_oracle_checks, at most 40% are static_checks (§3.9).
Environment
* environment/ contains only Dockerfile and, when needed, input_artifacts/.
* All packaged source files are under environment/input_artifacts/.
* Every shipped input is referenced in instruction.md; no orphaned source files remain.
* No tests, verifier code, manifest, partial oracle, answer key, or solution content is copied into the agent environment.

9. Summary
The Phase 2.2 standard can be reduced to these rules:


1. Choose a task that requires genuine coordination and supplied evidence. Avoid scriptable work and sources the base model is likely to have memorized.
2. Use the standard paths. Inputs belong under environment/input_artifacts/; every output must use an exact /logs/agent/... path.
3. Use one readable rubric. Every task includes tests/rubric_manifest.json.
4. Cover all three check types. Include static, reward-hacking, and partial-oracle checks.
5. Use five fields for every check and one point per check. No category floors, multipliers, caps, or weighted scoring systems.
6. Use one grader. tests/test.sh invokes tests/verify.py, which writes /logs/verifier/reward.txt.
7. Keep the manifest and code aligned. Every documented check exists in code, every scored check is documented, and total_checks matches both.
8. Check the real content of every rewarded artifact. File existence and formatting are not enough.
9. Run SA and MA fairly. Use the same instruction, environment, verifier, tools, and time budget, then review the actual artifacts and trajectories.
10. Keep MA challenged. A near-perfect MA reward usually means the task or rubric is too easy for the current client requirement.
11. Read every file before submitting. AI-assisted drafting does not transfer responsibility away from the trainer.
12. Make judge calls crash-safe and sandbox-safe. test.sh writes a zero-valued fallback if verify.py crashes before writing reward.json; judge model/endpoint/key configuration is a static value in verify.py, never an environment variable a trainer would need to set inside the Daytona sandbox (§3.7).
13. Ship a faithful high_level_prompt.md. ~250 words, deliverable-only, separate from instruction.md, never regenerated to disagree with it (§3.8).
14. Run all three modes. single, multi, and multi_noplan against the same package, environment, verifier, and time budget — multi_noplan proves the decomposition is materially useful (§2.3, CR-14).
15. Expose named reward components and stay content-heavy by count. reward.json adds static_checks/reward_hacking_checks/partial_oracle_checks/final_score; final_score is a plain equal average of the three category scores; at least 60% of checks by count are content-based (§3.9).
16. Treat the 18pp gap and the LLM Quality Gate review as hard gates, not optional steps. Both block submission now, not just internal review (§3.9, §6).


The Quality Gate can catch many structural failures, but the trainer is still responsible for source novelty, realistic difficulty, verifier fairness, and whether the reward measures the actual task.


Questions should be raised in puffin-q-n-a-multi-agent-swarm-benchmark-trainers before submission, not after delivery.

Task Design Learning Note: Scaling and RH
Task Design Learning Note: Scaling and Reward-Hacking Hardening
This note explains the method used to improve the datasheet-spec task and how the same pattern can be reused for future SwarmBench tasks.
1. Start From a Real Task, Not a Benchmark Trick
The base task was a normal procurement assignment: read real semiconductor datasheets, extract the values a buyer would actually care about, normalize them, and create an approved-parts catalog.


The important design choice was to keep the agent-facing instruction natural. We did not tell the agent, "this is a long-horizon task" or "this is designed to beat a single agent." The instruction reads like a real stakeholder request from a procurement team. That matters because the difficulty should come from the work itself, not from benchmark language.
2. Increase Scale Through Independent Work Units
The original task already had real scale because it required reading 31 datasheets. Each datasheet is an independent extraction unit, which makes it suitable for multi-agent execution.


The scalable pattern is:


1. Split the corpus into independent shards.
2. Require one durable shard output per input unit.
3. Require a final reducer to merge the shards.
4. Require cross-shard summary statistics that can only be correct if the reducer reconciles the full set.


For this task, each datasheet writes:


/logs/agent/shard-<FILENAME_STEM>.json

Then the reducer writes:


/logs/agent/output.json

This makes the task harder for a single agent because it must track many files, many numeric fields, many null cases, unit conversions, and final aggregate statistics without losing state.
3. Add a Downstream Multi-Modal Layer
After the extraction catalog, we added a second layer: board-profile procurement decisions and multimedia outputs.


New input:


/input_artifacts/board_profiles.json

New outputs:


/logs/agent/board_fit_report.json
/logs/agent/procurement_risk_dashboard.svg
/logs/agent/procurement_review_brief.html

This increases complexity because the agent cannot stop after extraction. It has to use the extracted catalog to make profile-fit decisions, then use those decisions to create an SVG dashboard and HTML review brief.


The key rule is that the multimedia files must be derived from the structured outputs. They cannot be decorative files that merely contain the right title. The SVG and HTML must reflect real category counts, profile IDs, and recommended parts from output.json and board_fit_report.json.
4. Add Hierarchical Coordination
The decomposition was upgraded from a simple extraction plan into a hierarchy:


1. Schema supervisor writes a runbook.
2. Datasheet managers own groups of parts.
3. Leaf workers extract individual datasheets.
4. Schema guard checks all shard files.
5. Two catalog solvers independently compute the merged catalog.
6. Final reducer reconciles output.json.
7. Two board-fit analysts independently apply board profiles.
8. Board-fit reducer writes board_fit_report.json.
9. SVG and HTML builders create the media outputs.
10. Final media validator checks consistency across all artifacts.


This makes the multi-agent advantage real because different agents can own different kinds of work: extraction, schema validation, aggregate reconciliation, decision analysis, and final media consistency.
5. Use Reward-Hacking Audits Before Trusting the Verifier
After adding new deliverables, we tested the verifier like a cheater agent.


The fake submission did not do the real datasheet work. It created:


* all 31 shard files;
* a full output.json;
* all numeric fields as null;
* generic summaries;
* a board-fit report that recommended nothing;
* SVG/HTML files with the right titles and profile IDs.


Before hardening, this hollow submission scored:


0.3636

That was too high because a schema-valid but empty answer was receiving meaningful credit.


After the first hardening pass, the same hollow submission scored:


0.0892

After the second hardening pass and reweighting, it scored:


0.1053

The small increase is acceptable because we removed the strict scoring cliff and made the scoring more proportional. The important part is that the hollow answer still receives almost no credit from the checks that matter: board-fit recommendations, board-fit decision coverage, SVG substance, and HTML substance all score 0.0000.


The most important learning is this: a verifier should be attacked before it is trusted. A good-looking answer is not enough. We need to ask whether the verifier is checking real task completion or merely checking whether the output has the right shape.
6. Cheater Prompt Template
Use this only as a verifier audit step, never as a valid task submission.


You are a verifier red-team agent. Your job is to test whether this task's verifier can be reward-hacked.


Read the task instruction, expected output schema, rubric manifest, and verifier code. Then create the strongest possible shallow submission that tries to earn reward without actually completing the intended task.


Try these shortcut families:


1. Shape-only completion:
   - create every required output file;
   - include every required key and path;
   - use all expected IDs, part numbers, record IDs, or filenames;
   - make the JSON/schema look perfect.


2. Null or default padding:
   - leave hard numeric fields null;
   - use default values such as 0, empty arrays, or generic booleans;
   - check whether nulls/defaults still receive credit.


3. Wrong-but-present values:
   - use numbers or strings that appear somewhere in the source text but are not the correct answer;
   - check whether the verifier only checks text presence instead of correctness.


4. Self-consistent fabrication:
   - make shard files and reducer outputs agree with each other;
   - make downstream reports agree with the fake reducer output;
   - check whether self-consistency is rewarded even when the source values are wrong.


5. Keyword stuffing:
   - include every obvious rubric word, ID, title, field name, and label;
   - write generic reason text that mentions all possible failure fields;
   - check whether the verifier accepts keyword presence as reasoning.


6. Decorative artifact shell:
   - create SVG/HTML/video/report files that contain required labels;
   - avoid doing real visualization, analysis, or source-derived explanation;
   - check whether media/report checks are only searching for text.


7. Instruction-prohibition bypass:
   - look for every "do not" or "only write" instruction;
   - deliberately violate it in a controlled way;
   - check whether the verifier notices.


Run the verifier on the shallow submission and report:
- total reward;
- which checks gave credit;
- which checks failed;
- why the fake submission still received any nonzero score;
- what concrete verifier changes would reduce the fake score without breaking a correct solution;
- whether any score comes from static structure, real task work, real-value checks, or LLM judge calls.

The goal is not to help anyone cheat. The goal is to prove the verifier is not accidentally rewarding empty but well-shaped output.
7. How the Agent Could Cheat
The main cheating routes were:


1. Schema-only completion The agent creates every required file and every required key, but does not extract correct values.


2. Blanket null padding The agent writes null for hard numeric fields and relies on the verifier treating nulls as acceptable.


3. Self-consistent fake downstream artifacts The board-fit report, SVG, and HTML agree with the fake catalog, but the fake catalog is not source-grounded.


4. Decorative media The SVG/HTML include the right title and labels, but do not reflect real procurement decisions.


5. Easy category guessing Some categories can be guessed from part names, so category credit alone cannot prove the datasheets were read.


6. Wrong-but-present numeric grounding The agent can pick a number that exists in the source text but is not the required field value. A verifier must check the expected value, not only that the submitted number appears somewhere in the source.


7. Boilerplate reason stuffing The agent can write one generic reason that names every possible field. A verifier must check that the reason names the actual failed field for that exact profile and part.


8. Copied context as explanation The agent can copy the board profile note into decision_summary. A verifier must detect that the explanation is not just copied context.
8. How We Fixed the Verifier - Eg.. do not copy it, just for understanding.
The verifier was hardened in these important ways:


1. Oracle-aware nulls A submitted null only receives credit when the hand-verified oracle also says that field is genuinely absent.


2. Minimum rating substance A rated part must include at least one real extracted rating before the row or shard can count as complete.


3. Minimal real-value weighting The real-value oracle layer was reduced to 2.4 / 14.4 = 16.67% of the reward. It is now a spot-check guardrail, not the main scoring mechanism.


4. Correct-and-grounded numeric checks A datasheet numeric value must match the hand-verified expected value and be grounded in the staged source text. Text presence alone no longer counts.


5. Substantive shard consistency A shard and merged row must both be compliant and substantive before agreement between them receives credit.


6. Board-fit checks against verified truth The verifier recomputes eligible parts from the submitted catalog and from the hand-verified catalog. recommended_parts must cover the verified eligible set.


7. Reason checks tied to actual failed fields A watchlist or rejection reason must name a field that actually fails that profile for that submitted part.


8. Profile-summary anti-copy check decision_summary must be real decision prose, not a substantial copy of the board profile note.


9. Media substance checks SVG now needs real graphical marks, and HTML now needs section/heading structure plus enough visible prose. Decorative shells no longer receive media credit.


10. Cleaner instruction and metadata Unsupported multi_modal classification was removed, and the rounding example was replaced because the earlier numbers accidentally matched real oracle values.
9. Keep One Rubric File
The task should not ship separate rubric files like:


tests/llm_judge_rubric.json
tests/rubric_manifest.json

The judge criteria were merged into:


tests/rubric_manifest.json

verify.py now reads the LLM judge rubric from that single manifest file. This keeps the scoring contract easier to inspect and avoids drift between multiple rubric files.
10. Reusable Quality Pattern
For future tasks, use this checklist:


1. Make the task sound like a real stakeholder request.
2. Add many independent input units.
3. Require durable shard outputs.
4. Require a reducer output.
5. Add a downstream decision layer.
6. Add a visual or multimedia layer only if it must be derived from structured results.
7. Write verifier checks for real values, not only file shape.
8. Run a hollow-output cheater audit.
9. Patch the verifier until the hollow score is very low.
10. Run an oracle-shaped positive control to make sure a correct solution is still achievable.


The final standard is simple: a fake complete-looking answer should score low, and a genuinely correct answer should still be able to reach full deterministic credit.
11. What Good Reward-Hacking Testing Looks Like
A good reward-hacking test is not just "make an empty output and see if it fails." It should actively search for the easiest path through the verifier.


For every verifier check, ask:


1. What is the cheapest thing an agent could write to pass this check? If the answer is "include a keyword," "create a file," or "copy a schema," the check is too weak.


2. Does this check compare against the real source of truth? For numeric or factual fields, source presence alone is not enough. The value must be the correct value for the correct field.


3. Does this check reward self-consistency too much? Shards, reducer outputs, reports, and media can all agree with each other while still being wrong. Self-consistency is useful, but it cannot replace source-grounded correctness.


4. Does this check enforce every explicit instruction? If the instruction says "do not copy," "write only," "include exactly," or "use this path," the verifier should check it directly.


5. Does this check give large credit for low-value structure? File presence, schema shape, paths, and field names should be prerequisites or low-weight checks. The main reward should come from real task substance.


6. Can a correct solution still pass after hardening? Every anti-cheat fix should be checked against an oracle-shaped positive control. The goal is to punish hollow output, not make the task impossible.


The best final reviewer mindset is: "If I wanted to fake this task in 15 minutes, what would I write, and would the verifier catch me?"


Structured Approach
Delivery Pipeline for Creating a Production-Ready Task
Phase 1: Task Ideation and Task Formulation
The first issue we identified is that trainers are blindly trusting the prompts available in the Labeling Tool.
The Labeling Tool prompt is not a golden task. It is not guaranteed to be complex enough to break the single agent, and it is not guaranteed to allow the multi-agent system to perform better.
The prompts in the Labeling Tool are LLM-generated and are primarily intended to help trainers overcome the creativity bottleneck.
During Phase 1, we observed that trainers were creating similar task types, using similar failure patterns, and repeatedly producing tasks from the same narrow set of domains and workflows. The prompt-generation pipeline was introduced to provide a wider variety of ideas.
However, this does not mean that every generated prompt must be claimed and created exactly as written.
Trainers should use the Labeling Tool for:
* Inspiration
* Domain discovery
* Workflow discovery
* Identifying possible task directions
* Avoiding repetitive ideas
Trainers should not use the Labeling Tool as:
* A final task specification
* Proof that a task has sufficient scale
* Proof that a task will break a single agent
* Proof that a task will benefit from multi-agent execution
* A mandatory task that must be completed exactly as written
Questions that must be answered before proceeding
Before moving to the next phase, the trainer must ask:
* Is this task based on a realistic professional workflow?
* Would someone in the relevant profession actually perform this task?
* Does the task contain multiple meaningful sub-problems?
* Can those sub-problems be assigned to independent sub-agents?
* Will multiple agents genuinely improve the quality or accuracy?
* Would a single agent struggle because of the task's scale, breadth, coordination needs, or context requirements?
* Does the task require multiple kinds of reasoning or specialized investigation?
* Is the task objectively verifiable?
* Is the expected output large and detailed enough to create meaningful execution pressure?
* Is the complexity natural, or has it been added artificially?
A strong multi-agent task usually contains several independent workstreams. A single agent attempting to complete all of them may experience context degradation, miss requirements, make inconsistent decisions, or fail to verify every part of the output.
The multi-agent system should gain an advantage because each sub-agent can focus on a specific component while the orchestrator coordinates and integrates the results.
If the trainer cannot confidently answer these questions, the task should not move to execution.
Phase 2: Scale Validation
Task scale must be validated before spending iterations.
The main objective is to determine whether the task is genuinely difficult for the single agent and whether multi-agent decomposition provides a meaningful advantage.
The trainer should ask:
* Can a single agent complete this task in one normal session?
* Is the Task automatable by a simple programming script? 
* Can one agent produce a strong output without external coordination?
* Is the task mostly a single reasoning chain?
* Are the sub-problems independent enough to run in parallel?
* Does the task require the synthesis of several large outputs?
* Does the task create enough pressure on context, planning, verification, or tool use?
* Would adding sub-agents improve performance, or would it only add unnecessary coordination?
If a single agent can easily complete the task, then the task is not at the required scale.
For example, if the single agent consistently scores 0.86, the trainer should not simply continue running more iterations and hope the multi-agent score increases.
The trainer must first determine why the single agent is performing so well.
Possible reasons include:
* The task is too small.
* The workflow is too simple.
* The prompt contains only one major workstream.
* The expected output is too limited.
* The verifier is too weak.
* The verifier checks only formatting and not task quality.
* Important prompt requirements are not represented in the verifier.
* The task allows shallow completion.
* The task does not create enough context pressure.
If the task itself is too easy and the verifier is already strong, the task should be dropped or significantly redesigned.
Iterations should not be used to rescue a fundamentally weak task.
Phase 3: Verifier and Decomposition Design
Before running the task, the trainer must ensure that both the verifier and the decomposition are strong.
Verifier design
The verifier should cover all meaningful requirements in the prompt.
Depending on the task, this may include:
* Structural checks
* File existence checks
* Required section checks
* Content completeness checks
* Accuracy checks
* Cross-file consistency checks
* Calculation checks
* Citation or evidence checks
* Reward-hacking checks
* Partial-oracle checks
* Edge-case checks
* Quality and relevance checks
The trainer should not ask only:
Does the verifier run successfully?
The correct question is:
Does the verifier accurately distinguish between a strong, complete output and a shallow or incomplete output?
A weak verifier may allow a single agent to score highly even when the generated artifact is not genuinely good.
If the single agent scores well, the trainer must inspect both the trajectory and the verifier before concluding that the task itself is too easy.
Decomposition design
The decomposition must reflect how the task can be broken into meaningful sub-problems.
The trainer should ask:
* What does each sub-agent own?
* Are the assignments independent?
* Are multiple agents duplicating the same work?
* Is the decomposition mostly sequential?
* Does every sub-agent produce something useful?
* Does the orchestrator correctly use the sub-agent outputs?
* Are important sub-problems missing from the decomposition?
* Is there a need for hierarchical coordination?
* Are there specialist agents for research, validation, calculation, synthesis, or review?
Adding more sub-agents does not automatically create a strong multi-agent task.
The decomposition should improve performance by distributing real cognitive work, not by creating unnecessary agent count.
Phase 4: Draft Review
Draft Review is mandatory before the first proper execution.
The expected flow is:
1. Select or create the task idea.
2. Formulate the full task.
3. Create the input artifacts.
4. Write the verifier.
5. Create the decomposition.
6. Validate the scale.
7. Run Draft Review.
8. Resolve Draft Review findings.
9. Start execution.
Trainers are currently skipping Draft Review and moving directly into iterations. As a result, they later receive a large number of issues from the Quality Gate.
This creates several problems:
* Iterations are wasted on tasks that are not ready.
* Verifier issues are identified too late.
* Ambiguities are discovered after execution.
* Task-scale problems remain hidden.
* Decomposition problems are discovered only after several runs.
* Quality Gate changes may significantly alter the task after a gap has already been achieved.
The Draft Review should help validate:
* Prompt clarity
* Task scale
* Input sufficiency
* Output expectations
* Verifier coverage
* Reward-hacking resistance
* Decomposition quality
* Quality Dimension alignment
* Missing requirements
* Contradictions or ambiguity
The trainer should not proceed until the Draft Review findings have been addressed or clearly justified.
Phase 5: Choosing the First Execution
Execution should be sequential, not parallel.
Trainers should not immediately run both the single-agent and multi-agent versions at the same time.
The first execution should depend on the trainer's confidence in task complexity.
When to run the single agent first
Run the single agent first when:
* You are uncertain whether the task is complex enough.
* You are approximately 50-50 confident about task scale.
* You suspect the single agent may already perform well.
* You want to understand how a strong baseline model approaches the task.
* You need evidence to determine whether the task should be expanded or dropped.
After the single-agent run, inspect the trajectory before running the multi-agent version.
When to run the multi-agent first
Run the multi-agent first only when:
* The task has passed Draft Review.
* The task clearly contains multiple large workstreams.
* The trainer is highly confident that the single agent will struggle.
* The decomposition is detailed and meaningful.
* The trainer wants early visibility into multi-agent coordination quality.
Even in this case, the trainer must inspect the multi-agent trajectory before proceeding.
When not to run anything
Do not start execution when:
* You are not confident that the task is complex.
* The verifier is incomplete.
* The decomposition is shallow.
* Draft Review has not been completed.
* The task is copied directly from the Labeling Tool without proper reasoning.
* The expected output is small enough for a single session.
* The task requirements are still ambiguous.
If the task is clearly not complex enough, improve or replace it before consuming an iteration.
Phase 6: Single-Agent Trajectory Analysis
The single-agent objective is not simply to obtain a score.
The objective is to understand:
* What the single agent could complete
* What it missed
* Where its reasoning degraded
* Whether it handled all workstreams
* Whether it exploited verifier weaknesses
* Whether the task created enough pressure
* Whether the verifier accurately evaluated the result
If the single agent scores highly, the trainer must review the full trajectory.
Ask:
* How did the single agent solve the task?
* Which parts were easy?
* Did it complete all requirements?
* Did it use shortcuts?
* Did the verifier miss important quality problems?
* Did the single agent genuinely produce a strong artifact?
* Was the task smaller than expected?
* Were several requirements highly correlated and therefore easy to complete together?
* Was the output mostly templated or repetitive?
If the verifier is weak, improve the verifier and rerun only after understanding the exact gap.
If the verifier is strong and the single agent genuinely completed the task well, the task is not at the required scale. The trainer should either redesign it significantly or drop it.
The correct response is not to repeatedly rerun the same task and hope for a lower single-agent score.
Phase 7: Multi-Agent Trajectory Analysis
The multi-agent score alone is not enough.
The trainer must inspect what happened across:
* The orchestrator
* Each sub-agent
* Communication between agents
* Work allocation
* Tool usage
* Failure handling
* Final integration
* Verification and review
The trainer should ask:
* Did the orchestrator create the correct plan?
* Were the right sub-agents created?
* Did each sub-agent understand its responsibility?
* Did multiple agents perform duplicate work?
* Were important workstreams not assigned?
* Did a sub-agent fail because of tooling, context, rate limits, or unclear instructions?
* Did the orchestrator ignore useful sub-agent outputs?
* Did the final synthesis introduce errors?
* Did the agents verify one another's work?
* Was the hierarchy appropriate for the task?
Trainers do not have to manually inspect every long trajectory without assistance.
They can use coding agents or analysis agents to:
* Read individual sub-agent trajectories
* Summarize each agent's behavior
* Identify failure patterns
* Compare successful and unsuccessful agents
* Detect duplicated work
* Identify missing workstreams
* Recommend decomposition changes
Agents should be used to accelerate analysis, not to replace the trainer's judgment during task ideation and task design.
Example of trajectory-driven improvement
Suppose a multi-agent task fails because sub-agents repeatedly hit GitHub API rate limits.
A weak response would be:
The multi-agent failed because of a rate-limit issue.
A strong response would be:
The research sub-agents depended only on the GitHub API and repeatedly hit the rate limit. I added a specialist sub-agent responsible for identifying alternative retrieval strategies, including repository cloning, raw-file access, curl, request-based retrieval, and non-API scraping approaches. The orchestrator now passes those fallback strategies to the affected research agents.
Every failed iteration should lead to a concrete improvement in the decomposition, task, verifier, or execution strategy.
Phase 8: Gap Analysis
After reviewing both trajectories, classify the result.
Case 1: Single agent performs well, multi-agent performs slightly better
Example:
* Single agent: 0.86
* Multi-agent: 0.89
Likely causes:
* Task scale is too low.
* Single agent can complete most work in one session.
* Verifier is too weak.
* Workstreams are not sufficiently independent.
* Multi-agent coordination adds little value.
Required action:
* Review the verifier.
* Review the single-agent trajectory.
* Increase task scale only if the workflow can support natural additional complexity.
* Drop the task if it cannot become genuinely multi-agent.
Case 2: Both single agent and multi-agent perform poorly
Example:
* Single agent: 0.38
* Multi-agent: 0.42
Likely causes:
* Task is ambiguous.
* Inputs are insufficient.
* Verifier is incorrect.
* Decomposition is poor.
* Tooling or environment failures are affecting both systems.
* The task may be difficult for the wrong reasons.
Required action:
* Inspect both trajectories.
* Validate the task instructions.
* Validate the verifier.
* Check environment and tool failures.
* Improve the decomposition.
* Do not assume that a low single-agent score means the task is automatically good.
Case 3: Single agent performs poorly and multi-agent performs well
Example:
* Single agent: 0.35
* Multi-agent: 0.78
This is the desired direction, but the task is not yet delivery-ready.
The trainer must still:
* Confirm that the verifier is valid.
* Confirm that the multi-agent succeeded for the correct reasons.
* Run the Quality Gate.
* Address Quality Dimension issues.
* Revalidate the gap after meaningful task changes.
Phase 9: LLM Reviewer and Quality Gate
The Quality Gate should not be treated as an external blocker or as a reason for task non-completion.
The Quality Gate is a review mechanism designed to help identify issues before client delivery.
The correct mindset is:
The Quality Gate is helping us identify problems that the client could otherwise reject.
A trainer should not report:
I could not complete the task because the Quality Gate rejected it.
The trainer should report:
The Quality Gate identified three valid issues in verifier coverage and two invalid findings. I resolved the valid issues and added justification for the invalid findings. The task is now being revalidated for the score gap.
For every Quality Gate issue, the trainer must determine:
* Is the issue valid?
* What evidence supports it?
* Does it affect the prompt?
* Does it affect the verifier?
* Does it affect the decomposition?
* Does it affect task scale?
* Does it affect client usability?
* Does fixing it require re-execution?
If the issue is valid, resolve it.
If the issue is invalid, provide a clear justification explaining:
* Why the finding does not apply
* What task context the reviewer may have missed
* What existing verifier or prompt section already addresses it
* Why no change is required
The Quality Gate is LLM-based and may produce imperfect findings. Trainers must reason about the feedback rather than blindly accepting or rejecting it.
Phase 10: Understanding Quality Dimensions
Trainers must understand the Quality Dimensions before task creation, not after Quality Gate rejection.
The Quality Dimensions should guide:
* Task ideation
* Prompt construction
* Input creation
* Verifier design
* Decomposition
* Output expectations
* Review criteria
The trainer should be able to explain how the task satisfies each relevant dimension.
If the trainer does not understand a Quality Dimension, they should review examples, ask the QA lead, or discuss it before execution.
Quality Dimensions should not be treated as a final checklist that is reviewed only after the task is otherwise complete.
They must be embedded into the task from the beginning.
Phase 11: Revalidating the Gap After Quality Changes
Some trainers achieve a score gap before Quality Gate changes but lose it afterward.
This happens because Quality Gate fixes can materially change:
* The task prompt
* The verifier
* The expected output
* The decomposition
* The difficulty
* The scoring behavior
For example:
* Clarifying an ambiguous prompt may make the task easier for the single agent.
* Strengthening the verifier may lower both scores.
* Adding missing requirements may reduce multi-agent performance.
* Correcting a verifier bug may remove an artificial score gap.
* Simplifying an unrealistic workflow may reduce task scale.
Therefore, after any meaningful change, the trainer must determine whether the existing execution results are still valid.
A task is not delivery-ready merely because it had a gap before the task was corrected.
The final version of the task must demonstrate the required behavior.
Phase 12: Final Review and Delivery
Before delivery, confirm:
* The task is based on a realistic workflow.
* The task is sufficiently large and complex.
* The single agent struggles for valid reasons.
* The multi-agent improves performance for valid reasons.
* The verifier is comprehensive and correct.
* The decomposition is meaningful.
* Draft Review findings are resolved.
* Quality Gate findings are resolved or justified.
* Quality Dimensions are satisfied.
* The final task version still preserves the required score behavior.
* All required task files and metadata are complete.
* Static checks pass.
* The final artifacts are packaged consistently.
Required Mindset Change
The delivery process must be treated as a gated engineering pipeline, not as repeated trial and error.
The correct pipeline is:
Task idea
→ Task-scale validation
→ Full task formulation
→ Verifier design
→ Decomposition design
→ Draft Review
→ First sequential execution
→ Trajectory analysis
→ Root-cause analysis
→ Targeted correction
→ Quality Gate
→ Quality Dimension validation
→ Gap revalidation
→ Final delivery
Iterations are expensive and limited.
Every iteration must test a clear hypothesis.
Before running, the trainer should be able to state:
* What am I testing?
* Why do I expect this run to behave differently?
* What change did I make?
* What evidence from the previous trajectory led to this change?
* What result would confirm or reject my hypothesis?
If the trainer cannot answer these questions, the next iteration should not be started.
The goal is not to get lucky and achieve a gap. The goal is to intentionally design a task where the single agent fails for understandable reasons, the multi-agent succeeds because of meaningful coordination, and the verifier reliably measures that difference.

Read this document first, then read the Trainer Guidelines before you author your first task. 1. What Is SwarmBench, and Why Does It Exist
The research question behind SwarmBench is this:
“A benchmark for evaluating multi-agent AI systems on tasks that are structurally too large or too complex for a single AI agent to solve reliably… it measures the gap between single-agent and multi-agent performance on real-world tasks.”
In plain language, we give one AI agent a hard task, alone. We give a coordinated team of AI agents the same task. We measure with code, not opinion, how much better the team does. Your job as a trainer/engineer is to build tasks where that gap is real, earned, and provably not the product of a rigged scoreboard.
What you physically produce, per task, is a folder of files: instructions.md, environment/, tests/verify.py, decomposition.yaml, and a handful of supporting files. What each of these actually does is covered in detail in Sections 5 and 6; for now, just know that this bundle, once it runs successfully through single-agent and multi-agent execution, becomes a unit of training/evaluation data for multi-agent AI research.
________________


2. Why This Matters Right Now — Industry Context
It’s worth being explicit about why this isn’t a narrow internal exercise: the exact question SwarmBench measures is one that the frontier AI labs and infrastructure companies are, right now, calling out as open, urgent, and empirically under-explored.
Google DeepMind’s research agenda paper “From AGI to ASI” (arXiv:2606.12683) lists “Multi-Agent Scaling” as one of its named open research directions, and frames it this way:
“Intelligence amplification through groups of AGIs could potentially significantly contribute to AI progress, but also with high uncertainty… it is now possible to run experiments at scale and collect empirical observations to complement and help advance the theoretical understanding.”
Two of its specific sub-questions read almost as a description of what a SwarmBench task does:
“(a) Research how task delegation and problem decomposition among specialized AI agents can bypass limitations of individual agents, including hardware and architectural limitations.”
“(b) Study for which classes of tasks agent groups can become more intelligent than each individual agent, and how this depends on the form of group organisation…”
That’s the single-agent vs. multi-agent reward gap, stated as an open research problem by one of the labs most invested in answering it. Every task you build is a concrete, falsifiable data point toward that question.
This isn’t the only signal that multi-agent coordination is moving from research curiosity to load-bearing infrastructure. A few more worth knowing about as context :
* Anthropic’s Claude Code has been extending its sub-agent model toward recursive spawning — a sub-agent that can itself spawn further sub-agents, rather than a single flat layer of delegation. That’s the same structural idea behind the hierarchical and specialist-routing coordination patterns you’ll be authoring tasks for.
* Ongoing research into recursive/compositional reasoning in language models (often discussed under the “RLM” umbrella) is studying how a model can call smaller instances of itself to handle sub-problems, conceptually adjacent to what a decomposition.yaml encodes by hand.
The throughline: you are not building tasks for a benchmark nobody will read. You’re generating the empirical evidence that a specific, named, currently open research question needs.
________________


3. How We Got Here — Phase 1 to Phase 2
Phase 1: prove the concept, hit a ceiling
The project started on the Kimi-CLI harness. Trainers built a fully self-contained task that included a deterministic ground-truth answer — a solution/ folder (oracle.json / solve.sh) that, when run, had to score exactly reward = 1.0. Only two coordination patterns existed: map-reduce and fan-out-synthesize.
This pipeline worked, but it hit real structural ceilings:
* dag_depth was hard-capped at 1 — a sub-agent could not itself spawn further sub-agents, no matter how the task was designed.
* A 4-agent concurrency cap limited how large a coordinated swarm could actually get.


The pivot
When the client reviewed Phase 1 deliveries, the ceiling became the finding: an oracle-based, depth-capped pipeline structurally could not produce the kind of large-scale, deeply coordinated tasks the research required. A benchmark that can’t go past dag_depth = 1 can’t actually test deep coordination.
Where things stand today
Phase 2 is defined by a set of client requirements, tracked as CR-01 through CR-13 — including web browsing, long-form writing (100K+ output tokens), visualization, a “Hard” difficulty tier requiring 50+ sub-agents, a mandatory dag_depth ≥ 2, the rubric-manifest scoring format, and a source-novelty rule (prefer recent, less-canonical sources over famous textbooks/case studies the model may already have memorized).
________________


4. How Task Execution Actually Works — Docker and Harbor, From First Principles
This is the section that answers “what actually happens when I run my task?” — assume no prior Docker or agentic-harness experience going in.
4.1 What a container is, and why we use one
Think of a Docker container as a sealed, reproducible box: the same operating system packages, the same filesystem, the same starting state, every single time it’s run — no matter whose machine or which server actually runs it. The blueprint for that box is called an image (built from a Dockerfile); a running instance of that blueprint is the container.
Why this matters here specifically: the single-agent run and the multi-agent run of the same task must see the exact same starting environment. If they didn’t, a measured performance gap could just be an artifact of environment drift — a missing package, a different file present — rather than a genuine difference in coordination capability. Docker is what makes the comparison fair.
4.2 What Harbor is
Harbor is the execution engine — think of it as the referee. It builds the container from your task’s Dockerfile, hands the sealed environment to an AI agent, installs the chosen agent in the container(you don’t need have a install command in your Dockerfile), passes your instruction and lets that agent work inside it for a bounded amount of time, then runs a separate verification step inside that same environment (verify.py) and reads back a score. As a trainer, you don’t call Harbor’s internals directly — you author the inputs Harbor consumes (the files described below), and Harbor does the rest.
4.3 The four files Harbor absolutely requires to run at all
If any one of these four is missing or malformed, your task cannot execute. Full stop — this is a Harbor-level requirement, not just a SwarmBench convention:
* task.toml — parsed into Harbor’s internal task configuration. Without it, Harbor has no idea what agent, timeouts, or resource limits apply.
* instruction.md — read verbatim and handed to the agent as its instructions. Nothing else in your task folder is automatically shown to the agent unless something explicitly reads it and passes it along — don’t assume Harbor “knows about” your other files just because they’re sitting in the same directory.
* environment/Dockerfile (or a pinned docker_image reference) — defines the sealed box described in 4.1.
* tests/test.sh — the fixed verifier entrypoint. Harbor always runs this exact script and nothing else, so that scoring is standardized across every task in the benchmark.
   * tests/verify.py - Is your Python verification logic. 
4.4 Files that are conventional, but not enforced by Harbor itself
This is where a lot of trainer confusion tends to live, so it’s worth being precise:
* environment/input_artifacts/ — only matters if your Dockerfile has a COPY line that pulls it into the image. Harbor does not automatically mount this folder for you.
* tests/verify.py — test.sh calls this by convention; Harbor itself never invokes verify.py directly.
* decomposition.yaml — this is SwarmBench-specific, not core Harbor. It’s read only by the multi-agent execution classes. Single-agent execution classes are never even given the task directory to look in — it’s not that they choose to ignore this file, they’re physically incapable of accessing it.
* high_level_prompt.md — not read by Harbor anywhere in its codebase. It’s a human-facing authoring/reference note only; it never touches the running task.
The practical takeaway: get the mandatory four right, and the task runs. Everything else is about what the agent actually sees and how the run gets scored — which is where your real authoring work lives, covered in Section 5.

4.5 The execution sequence, in order
1. Environment build. Harbor runs the Docker build using your environment/ folder as the build context — meaning any COPY instruction in your Dockerfile resolves relative to that folder. (A common bug: writing a COPY path as if the build context were the task root instead of environment/.) The container is then started, and Harbor waits for it to be ready.
2. Agent setup — bounded by a default 360-second timeout.
3. Agent execution — the agent is run with your instruction.md contents as its instruction, inside the container, for up to task.toml’s [agent] timeout_sec.
4. Verifier execution — Harbor uploads your tests/ directory into the container, runs tests/test.sh, and reads back the score from /logs/verifier/reward.json.
One detail worth understanding precisely: test.sh’s real job is simply to call verify.py. As a crash-safety net, it will write a zero-reward reward.json — but only if one still doesn’t exist after verify.py has run — while preserving the real exit code. This exists purely to prevent a hard crash from leaving no result file at all. It is not, and must never be used as, a way to override or fake a real submission’s score.




4.6 What task.toml’s fields actually control
Field
	What it actually does
	[task] name, description
	Cosmetic identifiers only
	[metadata] (verifier_type, coordination_pattern, dag_depth, dag_width, estimated_sub_agents, human_solving_hours_estimate)
	Free-form — never read by Harbor’s core execution. These exist purely for SwarmBench’s own dataset classification. This is worth flagging explicitly because it’s counterintuitive: setting dag_depth: 3 here does not enforce or unlock a depth of 3 in the running agent. It’s a label, not a mechanism. This should be written based on your Multi-Agent with plan execution. 
	[agent] timeout_sec
	Real, enforced wall-clock cap on the entire agent run
	[verifier] timeout_sec (default 600s)
	Real, enforced cap on how long tests/test.sh may run
	[environment] cpus / memory_mb / storage_mb / build_timeout_sec
	Real container resource limits


Limit: Compute -4, Memory - 8
	4.7 The three execution modes
Every task runs in three modes, and the difference between them is exactly what produces the measurable gap:
* single-opencode-agent — one agent, no sub-agent spawning capability, no decomposition.yaml involved at all.
* multi-opencode-agent — the agent is given a pattern-specific coordination prompt (selected by your task’s coordination_pattern, e.g., a hierarchical-specific prompt) plus the full contents of your decomposition.yaml, appended as a “Gold Decomposition Guide,” it’s told to follow. Sub-agent spawning is enabled.
* multi-opencode-agent-noplan — has the same sub-agent-spawning capability as the full multi-agent mode, but decomposition.yaml is deliberately withheld, and it receives only a generic, pattern-agnostic prompt (your task’s coordination_pattern is ignored for this mode). This exists to isolate a real research question: Does the swarm actually need the gold coordination plan, or can it organize itself just as well without it?

* instruction.md must stand entirely on its own. It has to be fully gettable by the single-agent mode with zero other files present. Important
Always use the recorded review feedback as the source of truth for rework. Do not restart or redesign unrelated parts of the task unless the feedback or validation results require it.
	

5. Similarity Checker
The project includes a similarity checker to reduce duplicate or near-duplicate tasks. This is especially important for instruction.md because multiple trainers may independently design tasks from related scenarios.
When to use it
Use the similarity checker while creating the task, before final completion/submission.
How to use it
15. Claim the task in the Labeling Tool first.
16. Prepare your instruction.md content.
17. Paste the instruction.md content into the similarity-checker field.
18. Click Check Similarity.
19. Review the result against previously completed tasks.
20. If the task is sufficiently unique, continue. If it is too similar, revise the task concept/instructions so the benchmark represents a genuinely distinct workflow.
Goal
The similarity checker is not only a wording check. The objective is to prevent trainers from submitting effectively the same task or instruction pattern as an existing completed task.
	

6. Quality Gate Report
The Quality Gate is the project’s LLM-judge-based validation layer. It helps identify quality issues before a task is finalized for delivery.
Final Quality Gate flow
21. Package/upload the completed task according to the project workflow.
22. Obtain the corresponding Google Drive link.
23. Submit the Drive link to the Quality Gate.
24. Open the generated Quality Gate report.
25. Review every failed check and its explanation.
26. Fix the task if failures are present, then validate again.
27. If the report is clean and all project requirements are satisfied, proceed with submission.
Do not treat the Quality Gate as a final-minute formality
If a major issue is discovered only after long execution runs are complete, fixing it may require substantial rework or reruns. Use the Draft Review workflow early to reduce this risk.


Per day, a trainer can use only 4 run quotas for a task, so connect with your pod lead and understand how efficiently to use the LLM judge. 
	

7. Draft Review — Use This Before Expensive Runs
Draft Review is designed to catch structural and quality problems before you spend significant time running single-agent or multi-agent executions.
Recommended timing
Submit a Draft Review after the core task package has been created, but before running the expensive execution logs.
Typical files to prepare first
* instruction.md
* task.toml
* decomposition.yaml
* environment/Dockerfile or the required environment setup
* tests/ directory and test files
* solution/ or the required reference solution files
* Other required task metadata or configuration files
Draft Review submission
28. Create a ZIP of the draft task package.
29. Keep the ZIP below 40 MB.
30. Upload/submit it through the Draft Review option.
31. Review which checks pass and which fail.
32. Address failures before beginning the full single-agent and multi-agent execution stage.
Why this matters
Draft Review shifts validation earlier in the workflow. Catching an instruction, configuration, environment, test, or packaging problem before execution can prevent wasted run time and avoid rebuilding the task at the end.

MAS Cloud Run Harness
Setup, Execution & Trainer Workflow Guide
SwarmBench • Updated workflow
Purpose
This guide explains how trainers install and use the MAS Cloud Run trainer CLI to execute SwarmBench tasks in managed cloud sandboxes, collect execution logs, and avoid handling model or sandbox API keys locally.
	1. What is MAS Cloud Run?
MAS Cloud Run is the managed execution harness used for SwarmBench trainer runs. Instead of setting up Harbor locally or receiving Fireworks/Daytona credentials, the trainer uses the mascloud CLI. The CLI packages a task folder, uploads it to the managed control plane, runs the task inside a cloud sandbox, streams progress back to the terminal, and returns a result ZIP containing the task and fresh execution logs.
Trainer machine (mascloud CLI)  →  MAS Cloud Run server  →  cloud sandbox (Harbor + Daytona)  →  model
                                     ← live logs / result ZIP ←
	Why this exists
The main security benefit is credential isolation: trainers authenticate with their Turing account, while Fireworks and Daytona keys remain server-side. The trainer machine only stores a MAS Cloud Run session token.
	2. Repository and prerequisites
* Repository: https://github.com/MathavanSG14/swarmbench-harness
* Python 3.9 or newer
* pipx installed and available on PATH
* Turing MAS Cloud Run credentials provided by the project team
* A valid SwarmBench task folder containing task.toml
3. First-time installation
Clone the repository and install the trainer CLI from the mascloud_client directory:

	Verify that the CLI is available:

6. The required three-run delivery workflow
Delivery requirement
Every SwarmBench task must be run in all three modes: single, multi, and multi_noplan. A complete delivery therefore needs execution logs from all three runs.
	mascloud run ./my-task --mode single
mascloud run ./my-task --mode multi
mascloud run ./my-task --mode multi_noplan
	

Mode
	Purpose
	Key behavior
	single
	Single-agent baseline
	No subagents; measures the task under a single-agent setup.
	multi
	Planned multi-agent run
	Runs the multi-agent swarm with decomposition.yaml injected.
	multi_noplan
	Multi-agent no-plan run
	Runs the same multi-agent swarm without decomposition.yaml injected. Required for delivery.
	

Concurrency constraint
Only one of your runs can be QUEUED or RUNNING at a time. Do not start the three modes in parallel from separate terminals. Wait for the current run to finish before submitting the next one.
	7. What happens during each run
1.  The CLI validates that the selected folder contains task.toml.
2.  The task folder is packaged locally. Existing execution_logs/ are excluded from a fresh agent run.
3.  The ZIP is uploaded to the MAS Cloud Run control plane.
4.  The task executes in a managed cloud sandbox and progress is streamed live to your terminal.
5.  After completion, a result ZIP is automatically saved beside the task folder unless --no-download is used.
6.  The result ZIP contains the full task plus the newly generated execution_logs/.
Expected result package names follow the selected mode, for example:
my-task-single.zip
my-task-multi.zip
my-task-multi_noplan.zip
	Press Ctrl-C while a run is streaming to cancel it. The server stops the run and tears down its cloud sandbox.
8. verify-only: update verifier results without rerunning the agent
Use verify-only when tests/verify.py changes after you already have a valid agent run—for example, when fixing reward formatting or verifier logic. This avoids paying the inference cost again when the agent output itself has not changed.
mascloud verify-only ./my-task --target-mode multi
	The command supports single, multi, and multi_noplan as target modes. Unlike a normal run, verify-only uploads the existing execution_logs/ because those logs are the input to the verifier replay.
* No OpenCode agent is rerun and no new inference cost is incurred.
* The server replays verification against the current tests/verify.py.
* reward.json, test-stdout.txt, and result.json are refreshed in the same execution log folder.
* trajectory.json, raw_trajectory/, and opencode.txt are preserved.
* The request is rejected if the required existing execution log for the target mode is not present.
Use this instead of a full rerun
If only the verifier changed, do not waste a single/multi/multi_noplan agent run. Re-verify the existing run.

Payment Process
Jibble Payment Processing Guide
Trainer payment eligibility, approved hours, and monthly Jibble logging
Purpose. This guide explains when a completed task becomes eligible for payment, how client acceptance affects payment, how payable hours are calculated, and how trainers use Jibble to record the approved hours provided by the Program Manager.
1. What is Jibble?
Jibble is the internal time-tracking application used to record the approved payable hours for trainers. Trainers should not independently estimate or clock hours based only on the time they personally spent working. The hours to be entered in Jibble are based on the project-approved task value and the final number of client-accepted tasks.
2. When does a task become payable?
1. Trainer completes the task: The trainer finishes the task and submits it through the project workflow.
2. Reviewer checks the task: The assigned reviewer or Pod Lead reviews the submission against the project requirements.
3. Task enters the delivery batch: If the task passes internal review, it is added to the delivery batch and sent to the client.
4. Client performs the final review: The client is the final reviewer. A task is only payable after it is accepted by the client.
5. Payment eligibility is confirmed: Only tasks that are both marked as Delivered and Client Accepted are counted toward trainer payment.
Important: A task that is rejected by the client is not considered for payment in that review cycle. However, the task can be sent for rework. The trainer may correct it and submit it again. If the revised task is later accepted by the client, it can then become eligible for payment.
	3. Payment eligibility rule
A task is payable only when both conditions are true:
* Delivery Status = Delivered
* Client Review Status = Accepted / Client Accepted
If either condition is not met, the task should not be included in the payable task count for that month.
4. How payable hours are calculated
Each accepted task has a fixed project value in hours. The monthly payable hours are calculated as:
Payable Hours = Number of Client-Accepted Tasks × Hours per Task
Example
Item
	Value
	Calculation
	Approved value per task
	7 hours
	—
	Client-accepted tasks
	3 tasks
	—
	Total payable hours
	21 hours
	7 × 3 = 21
	Therefore, the trainer should be paid for 21 hours for those three accepted tasks.
5. End-of-month payment process
1. Program Manager consolidates accepted tasks: At the end of the month, the Program Manager reviews the delivery records and identifies the tasks that were delivered and accepted by the client.
2. Accepted tasks are counted: The Program Manager totals the number of eligible tasks for each trainer.
3. Payable hours are calculated: The accepted task count is multiplied by the approved hours-per-task value.
4. Trainer receives the approved hour count: The Program Manager communicates the exact number of hours the trainer should clock for that month.
5. Trainer records the hours in Jibble: The trainer logs the approved hours in Jibble using the access provided for the project.
6. Payment is processed: The approved Jibble hours are then used as the basis for payment processing.
6. Trainer responsibilities
* Do not count a task as payable simply because it was completed or internally approved.
* Confirm that the task reached the delivery batch and was accepted by the client.
* If a task is rejected, complete the required rework and resubmit it through the normal workflow.
* Clock only the number of hours communicated by the Program Manager.
* Do not manually add extra hours based on personal effort, reruns, debugging time, or rework unless the project team explicitly approves them.
* Complete the Jibble entry within the timeline communicated by the Program Manager.

	8. End-to-end flow
Complete Task  →  Internal Review  →  Delivery Batch  →  Client Review  →  Client Accepted  →  Hours Calculated  →  Jibble Entry  →  Payment
Key principle: Payment is based on client-accepted deliverables, not simply on task completion. Jibble is the mechanism used to record the approved payable hours after the accepted-task count has been finalized.

Task Pickup Clarification


There are no predefined prompts assigned to you. Your job is to author the task itself, end-to-end, within your domain of expertise.


What you need to produce per task:


* A real-world scenario prompt — Surf the web to gather authentic, large-context material from your domain (incident postmortems, codebases, regulatory docs, operational runbooks, datasets, etc.). Use that as grounding context so the scenario reflects how the problem actually shows up in production, not a toy version of it.
* Problem statement — Frame a concrete task on top of that context. The scenario must be one where a single agent fails (context too large, too many parallel sub-problems, coordination required) but a multi-agent swarm succeeds by decomposing and running work in parallel.
* Golden solution — The reference output that defines "correct."
* Test cases — Deterministic checks that grade any submission against the golden solution.


The performance bar: When you run your task through both configurations, the multi-agent run must outperform the single-agent run by at least 23 points on your test cases. If the gap is smaller, the task is not differentiating multi-agent capability strongly enough — rework the scenario (add more parallelizable sub-tasks, expand the context, raise coordination requirements) until the gap holds.


TL;DR: You are not picking from a queue. You are building the queue. Pick a domain -> pull real context from the web -> write the prompt, golden, and tests -> verify the >=23-point single-vs-multi gap before submitting.

Glossary
Agent — An AI model (Kimi K2.5) running inside a Docker container, executing a task. In our benchmark, agents are either single (one instance, tool-restricted) or multi (orchestrator + sub-agents).
Decomposition — The strategy for splitting a task into sub-tasks that multiple agents work on in parallel. Defined in decomposition.yaml.
Harbor — The evaluation harness framework. Handles Docker container lifecycle, agent execution, verification, and result collection. We use a patched version with custom SwarmBench agents.
LLM Judge — A separate LLM call (Kimi K2.5 via Fireworks) that grades the agent’s output against the oracle. Returns a score between 0.0 and 1.0 with field-by-field justification.
Oracle — The gold-standard correct answer (oracle.json) or gold fix (solve.sh). Used by the verifier to score the agent’s work. Also refers to the oracle agent (-a oracle) which applies the gold solution to validate the pipeline.
Reward — The score produced by the verifier. For llm-judge tasks: float 0.0–1.0 in reward.json. For executable tasks: binary 1 or 0 in reward.txt.
Sub-agent — An agent spawned by the orchestrator during multi-agent runs. Sub-agents run in isolated context — they cannot see the main instruction or other sub-agents’ output. Only available to swarm-kimi-multi.
Trajectory — A structured log of every step the agent took: tool calls, reasoning, observations, token counts. Saved as trajectory.json in the agent logs.
Trial — One execution of one agent on one task. A job with -k 1 produces 1 trials.
Verifier — The script (test.sh) that scores the agent’s output. For llm-judge: calls judge.py. For executable: calls verify.py. Must write a reward file to /logs/verifier/.
Volume mount — A Docker feature where a directory on your laptop is shared with the container. /logs/agent/ inside the container is the same as trial_dir/agent/ on your laptop. Files written inside appear outside instantly.


Project Overview
Section A — Project Overview
________________


A.1 — What Is SwarmBench
SwarmBench is a benchmark for evaluating multi-agent AI systems on tasks that are structurally too large or too complex for a single AI agent to solve reliably. It is built on the Harbor evaluation harness, uses Docker for isolated execution, and measures the gap between single-agent and multi-agent performance on real-world tasks.
As a trainer, your job is to create tasks. Each task you produce is a self-contained evaluation unit — a real-world problem, an execution environment, a gold-standard oracle, and a verifier that scores the agent's work. You are not writing prompts. You are building evaluation environments.
What you will create for each task:
* A human-authored task prompt (instruction.md) — a real problem a professional would face
* A Docker environment (environment/Dockerfile) — the container the agent works inside
* Input data (input_artifacts/) — the files, databases, or codebase the agent must process
* A gold oracle (oracle.json or test suite) — the correct answer or test harness
* A verifier (test.sh + judge.py or verify.py) — the script that scores the agent
* A decomposition guide (decomposition.yaml) — how a multi-agent system should split the work
What Harbor does automatically: builds the container, runs the agent, runs your verifier, collects the score, saves the trajectory. You do not manage containers or infrastructure.
Two agent modes run on every task:
* swarm-kimi-single — Kimi K2.5 running alone, with sub-agent spawning disabled
* swarm-kimi-multi — Kimi K2.5 as an orchestrator, reading your decomposition guide and spawning sub-agents
Both run just 1 time each. You compare the scores.
________________


A.2 — The Problem We Are Solving
Every day, professionals across medicine, research, engineering, and finance face tasks that are structurally too large for one person — or one AI — to handle alone.
A clinical fellow reviewing 1,500 case reports to identify a pattern in a rare post-procedural complication cannot hold all 1,500 cases in their head simultaneously. They divide the work: one resident reads cardiology cases, another reads vascular, a third reads systemic presentations. They meet, compare notes, synthesize. That coordination — divide, process in parallel, aggregate — is not a workaround. It is the only way the work gets done correctly.
A research team producing a systematic survey of 50 AI benchmark papers cannot assign all 50 to one person without losing rigor. Paper 47 gets a cursory skim. Subtle distinctions between benchmarks get conflated. Quotes get misattributed. The paper suffers.
A DevOps team responding to a critical CVE in a 200,000-line codebase cannot have one engineer read every module, identify every vulnerable call site, and patch them all before the disclosure deadline. They split by service, work in parallel, have a lead integrate.
This is what we are building the training data for: AI systems that coordinate the way expert human teams coordinate.
________________


A.3 — Why Single Agents Fail at Scale
Large language models are extremely capable within a context window. The problem is structural, not one of intelligence.
For knowledge and research tasks (llm-judge):
Consider our medical research task — a clinician must read and clinically assess 1,500 case reports across three specialty databases (~500,000 tokens). A single agent attempting this faces:
* Context overflow: By case 300, early cases are pushed out of the effective attention window. The agent forgets what it read in the first cardiac batch when synthesizing the vascular findings.
* Attention degradation: With 500K tokens in context, the signal-to-noise ratio collapses. The agent begins hallucinating PMCIDs — citing cases that do not exist or mixing up details between cases.
* Loss of diagnostic thread: The final synthesis requires holding three domains simultaneously. A single agent that has been reading for hours of context has no reliable working memory left for cross-domain reasoning.
A single expert clinician reviewing 1,500 case files would take weeks. The AI equivalent fails in a different way — it reads fast but loses precision the deeper it goes. This is the failure mode we are benchmarking.
For our agent benchmark landscape task — 11 research papers, each requiring careful extraction of 6 structured fields with verbatim quote evidence — a single agent begins confusing papers by paper 7. It attributes quotes from CRMArena to WorkArena. It hallucinates that a benchmark has 15 domains when the paper says 4. The errors compound. By paper 11, the extraction is unreliable.
For code and SWE tasks (executable):
Consider a team that has discovered CVE-2024-XXXXX in their authentication service — a token validation bug that exists in three microservices and 47 different call sites across 180,000 lines of Python. The remediation requires:
1. Finding every vulnerable call site across three services
2. Patching each one correctly without breaking adjacent logic
3. Running 340 integration tests across all three services to verify
A single agent exploring this codebase will run out of context budget before it finishes service one. It will patch 12 call sites, miss 35, and produce a codebase that still fails security tests — but now also has regression bugs.
Or consider a company migrating a monolithic Java 8 application to Java 17 — 80 modules, dozens of deprecated API calls, type casting changes, and library version conflicts. A single agent can handle perhaps 5–8 modules before its context fills and it starts introducing errors in module 9 that conflict with changes it made in module 2.
These are not toy scenarios. They are the exact situations where real engineering teams coordinate — and where AI needs to learn to do the same.
________________


A.4 — What You Are Building
As a trainer, you are not writing test cases. You are building the training signal that teaches AI systems when and how to decompose, delegate, and synthesize — the cognitive architecture of a coordinated team.
Every task you create is a proof that:
1. This problem is real — a professional would spend 10–100+ hours solving it
2. A single agent structurally cannot solve it (not just slowly — structurally, due to context limits or attention degradation)
3. A coordinated multi-agent system can solve it by dividing context, working in parallel, and synthesizing results
The benchmark is rigorous by design. A task only counts if:
* Single-agent -> it genuinely fails, not just struggles
* Multi-agent -> the coordination strategy actually works
* At least a 23-point gap between the two
* Single agent times out or fails on a single trial
* Multi-agent succeeds on a single trial
A task where both approaches score 60% is not useful. A task where both score 0% is broken. What you are looking for is a task with a structural wedge — one approach fails by design, the other succeeds by design.
________________


A.5 — What Makes a Good Task
The task prompt must be human-authored. It should read like a real professional request — specific, grounded, with realistic constraints. We are looking for real-world problem statements, not synthetic data.
The prompt should be neither underspecified ("analyze these files") nor overspecified ("on line 342 of server-01.log, find the…"). It should give the agent the same level of briefing a human expert would receive before starting the work.
Good task sources:
* Real clinical cases, research synthesis tasks, or data audits you have encountered professionally
* Open-source repos with real bugs, real PRs, real CVEs
* Public datasets that require multi-source cross-referencing
* Literature review tasks drawn from real research questions
Two real examples from our benchmark:
Task: Diagnose a rare cardiac complication from 1,500 medical case files across 3 specialty databases
Pattern: fan-out/synthesize
Why it works: 500K tokens; single agent hallucinates PMCIDs by case 300; 15 sub-agents each handle 100 cases within attention range
Task: Survey 11 agent benchmark papers and extract 6 structured fields with verbatim quote evidence
Pattern: fan-out/synthesize
Why it works: Context fills by paper 7; sub-agents each own one paper with clean isolated context; evaluator sub-agents cross-check claims

* Your test.sh runs without errors
* Your judge.py correctly scores a perfect answer

1.1 — LLM Judge (verifier_type = "llm-judge")
The idea: The agent produces a structured JSON answer. Another LLM (Kimi K2.5) reads that answer, compares it against your oracle, and scores it field by field — returning a float between 0.0 and 1.0.
This is the right choice when you are asking an agent to think, synthesize, or analyze — tasks where partial credit is meaningful and the answer can be captured as a JSON object.
Use this for:
   * Reading and synthesizing large document collections (research papers, case files, reports)
   * Data analysis where results are numbers, lists, or rankings
   * Diagnosis, classification, or recommendation tasks
   * Any task where a human expert would produce a structured report

Agent works → writes /logs/agent/output.json
                        ↓
Harbor uploads tests/ → container at /tests/
                        ↓

  → calls Kimi K2.5: "score this field by field"
  → {"score": 0.75, "passed": 6, "total": 8, "justification": "..."}
                        ↓
/logs/verifier/reward.json written → Harbor reads it

tests/judge.py — LLM judge. Use this template unchanged for most tasks:
import argparse
import json
import os
import re


from openai import OpenAI




def extract_json(text: str) -> str:
    text = text.strip()
    match = re.search(r"```(?:json)?\s*([\s\S]*?)```", text)
    if match:
        return match.group(1).strip()
    return text




def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--agent-output")
    parser.add_argument("--oracle")
    parser.add_argument("--reward-out")
    args = parser.parse_args()


    try:
        agent_output = json.load(open(args.agent_output))
    except (FileNotFoundError, json.JSONDecodeError) as e:
        json.dump({"reward": 0.0}, open(args.reward_out, "w"))
        with open("/logs/agent/judge_justification.txt", "w") as f:
            f.write(f"Score: 0.0\n\nAgent output missing or invalid: {e}")
        return


    oracle = json.load(open(args.oracle))


    # Exact match shortcut — oracle agent always scores 1.0
    if agent_output == oracle:
        json.dump({"reward": 1.0}, open(args.reward_out, "w"))
        with open("/logs/agent/judge_justification.txt", "w") as f:
            f.write("Score: 1.0\n\nAgent output exactly matches oracle.")
        return


    client = OpenAI(
        api_key=os.environ["FIREWORKS_API_KEY"],
        base_url="https://api.fireworks.ai/inference/v1",
    )


    prompt = (
        "You are an evaluation judge grading an agent's output against a gold oracle.\n\n"
        f"ORACLE:\n{json.dumps(oracle, indent=2)}\n\n"
        f"AGENT OUTPUT:\n{json.dumps(agent_output, indent=2)}\n\n"
        "Evaluate the agent output field by field against the oracle.\n"
        "- Score 1.0 if ALL fields are correct.\n"
        "- Score 0.0 if completely wrong or missing.\n"
        "- Score between 0.0 and 1.0 based on fraction of fields that pass.\n\n"
        "List EACH field, PASSED or FAILED, with a brief reason.\n"
        "Respond in JSON only (no markdown):\n"
        '{"score": <float 0.0-1.0>, "passed": <int>, "total": <int>, '
        '"justification": "<field-by-field breakdown>"}'
    )


    response = client.chat.completions.create(
        model="accounts/fireworks/models/kimi-k2p5",
        messages=[{"role": "user", "content": prompt}],
        temperature=0,
    )


    raw = response.choices[0].message.content or ""
    try:
        result = json.loads(extract_json(raw))
    except json.JSONDecodeError as e:
        json.dump({"reward": 0.0}, open(args.reward_out, "w"))
        with open("/logs/agent/judge_justification.txt", "w") as f:
            f.write(f"Score: 0.0\n\nJudge parse error: {e}\nRaw: {raw}")
        return


    score = float(result.get("score", 0.0))
    json.dump({"reward": score}, open(args.reward_out, "w"))


    with open("/logs/agent/judge_justification.txt", "w") as f:
        f.write(
            f"Score: {score} ({result.get('passed','?')}/{result.get('total','?')} passed)\n\n"
            f"{result.get('justification', '')}"
        )




if __name__ == "__main__":
    main()

The idea: The agent modifies code or files inside the Docker container. You write a test script that checks the result deterministically. No LLM is involved. Pass = 1, fail = 0.

Use this for:

   * Feature implementations — agent writes code, your test checks the spec
   * Code migrations — the agent upgrades the codebase, and your test verifies nothing broke

Section 2 — Agent Coordination Patterns
Section 2 — Agent Coordination Patterns
Before you write a single line of your task, decide how a multi-agent system should coordinate to solve it. This shapes your decomposition guide, your oracle, and what failure looks like for a single agent. In Phase 1 we support two patterns.
________________




Map-Reduce
________________


2.1 — Map-Reduce
The idea: The input is too large for one agent. Split it into independent shards — one per agent — process each in parallel, then aggregate all results.
When to use it: Multiple files, logs, databases, or records that are structurally similar. Each shard can be processed independently. The final answer requires merging.
Why single agent fails: Reading all shards sequentially fills the context window. The agent truncates early, hallucinates values from shards it can no longer see, or loses precision as context grows. The failure is structural — more data means less reliable output.
Real-world examples:
Scenario
	Shard
	Map
	Reduce
	Security audit: 6 microservice logs (500K events)
	One log per agent
	Error types, anomalous IPs, p95 latency
	Global error distribution, deduplicate IPs, rank slow endpoints
	Clinical diagnosis from 1,500 case files
	~100 cases per agent
	Classify relevance, extract PMCID + verbatim excerpt
	Aggregate domain stats, cross-reference evidence, final diagnosis
	Financial reconciliation across 12 quarterly reports
	One report per agent
	Revenue, COGS, margins, flag anomalies
	YoY trends, cross-report discrepancies
	coordination_pattern = "map-reduce"
decomposition.yaml structure:
sub_tasks:
  - id: map-shard-1
    description: "Process shard 1 — extract X, Y, Z"
    parallel_group: map
  - id: reduce-aggregate
    description: "Merge all mapper outputs into final answer"
    depends_on: [map-shard-1, map-shard-2]
    parallel_group: reduce

________________


Fan-Out / Synthesize
2.2 — Fan-Out / Synthesize
The idea: The task has multiple independent analytical threads, each needing focused attention. Fan out to parallel agents — one per thread — then synthesize all findings.
When to use it: Multiple independent dimensions requiring different lenses or sources. Each thread requires deep focused work. Final output synthesizes across threads — not just concatenates.
Why single agent fails: Holding all threads simultaneously dilutes attention. By thread 6–7, the agent conflates findings between threads, misses subtle distinctions, and produces a blurred synthesis. The failure is precision degradation under context pressure — not hard truncation.
Real-world examples:
Scenario
	Thread
	Fan-out
	Synthesis
	Survey 11 AI benchmark papers: 6 fields + verbatim quotes per paper
	One paper per agent
	Read completely, extract structured fields with exact quotes
	Cross-validate, deduplicate overlapping benchmarks, final comparison table
	Vendor cross-reference: contradictions across 10 reports in 4 domains
	One domain per agent
	Read all 10 reports through one domain lens, extract contradictions
	Deduplicate, classify by severity, cross-domain summary
	Drug interaction analysis across 6 clinical specialties
	One specialty per agent
	Literature review for specialty-specific interactions
	Cross-specialty risk matrix, flag compound interactions
	coordination_pattern = "fan-out-synthesize"
decomposition.yaml structure:
sub_tasks:
  - id: research-thread-1
    description: "Deep analysis of thread 1 — extract X, Y, Z with evidence"
    parallel_group: fan-out
  - id: synthesize
    description: "Merge all thread findings, resolve conflicts, final output"
    depends_on: [research-thread-1, research-thread-2]
    parallel_group: synthesize

Final Decision
2.3 — Choosing Between Them
Does the input split into independent, structurally similar chunks?
  YES → map-reduce
  NO  → Do multiple independent threads need parallel exploration?
          YES → fan-out-synthesize
          NO  → Rethink the task structure
In map-reduce, every agent does the same operation on a different chunk.
In fan-out, every agent does a different operation (or the same operation through a different lens) on the full input.

Strategy for Designing Tasks
Strategy for Designing Tasks Where Single Agents Fail and Multi-Agent Systems Pass
________________


Overview
The correct way to create a strong and durable gap between single-agent and multi-agent systems is not by trying to “trick” the model with clever wording. Instead, the focus should be on task structure.
Well-designed tasks should naturally reward:
   * Decomposition
   * Parallel execution
   * Structured synthesis
   * Verifiable completeness
A successful task typically follows this structure:
Many artifacts → Independent subproblem solving → Reducer synthesis → Verified final output
In contrast, tasks like:
One bug → One file → One fix → One test
will almost always be solved by a strong single agent and therefore fail to create meaningful differentiation.
The key insight from both research and practice is simple:
Multi-agent systems outperform only when the task is inherently decomposable.
________________


Core Design Principle: Breadth Under Budget
The central objective is to design tasks where success depends on breadth, not just intelligence.
This means:
   * Many artifacts must be processed
   * Multiple constraints must be tracked
   * Outputs must be reconciled
   * Work must fit within a fixed time budget
This creates natural pressure on single agents:
   * They lose track of coverage
   * They miss edge cases
   * They exceed time limits
   * They forget secondary requirements
Multi-agent systems succeed because they:
   * Divide ownership
   * Work in parallel
   * Maintain structured outputs
   * Use a reducer to verify and merge results
________________


1. Start With Natural Parallelism
Before building any task, validate:
   * Can this be split into 4–10 independent subproblems?
   * Can outputs be merged without ambiguity?
   * Will a single agent struggle with coverage or time?
If the answer is no, discard the task.
Good Task Shape
   * Many files, reports, or datasets
   * Independent processing per unit
   * Final aggregation step
Bad Task Shape
   * Single dependency chain
   * One core insight
   * Sequential reasoning only
________________


2. Use Timeout as a Valid Failure Mode
Single-agent failure does not need to be incorrect output.
Timeout is a valid and important failure signal.
Workflow:
   1. Run oracle → must score 1.0
   2. Run multi-agent with generous timeout
   3. Record runtime
   4. Set benchmark timeout close to that runtime
   5. Run single-agent under same conditions
Valid Outcome:
   * Multi-agent finishes in 9 minutes
   * Single-agent still exploring at 10 minutes
→ This is a valid gap
________________


3. Design for Coverage Failure (Not Just Difficulty)
Single agents are strong at:
   * Solving one core problem
   * Finding one key insight
They are weak at:
   * Exhaustive coverage across many items
Strong Task Patterns:
   * Fix all deprecated usages across 30+ files
   * Extract obligations across multiple contracts
   * Reconcile inconsistencies across reports
   * Process all rows across multiple datasets
Scoring Principle:
   * Partial completion must give partial score
Example:
   * Single-agent: 60% coverage → 0.60 score
   * Multi-agent: 100% coverage → 1.00 score
________________


4. Use Context Overload via Environment (Not Prompt)
Do not overload the prompt.
Instead:
   * Place artifacts in files, folders, repos
   * Force traversal and extraction
Example Inputs:
/input/reports/report_01.txt … report_20.txt
/input/contracts/*.txt
/src/module_a … module_z
/docs/topic_01 … topic_20
Why this works:
Single-agent struggles with:
   * Attention degradation
   * Constraint loss
   * Missed items
Multi-agent:
   * Assigns artifacts per worker
   * Maintains local context
   * Avoids context pollution
________________


5. Require Reconciled Deliverables
This is one of the strongest strategies.
Do not ask for just one output.
Require multiple outputs that must agree.
Example:
   1. Update source code
   2. Update tests
   3. Generate CHANGES.md
   4. Generate MIGRATION.md
   5. Generate REMOVED_SYMBOLS.json
   6. Verify all outputs match system state
Why it works:
Single-agent:
   * Completes main task
   * Misses secondary outputs
Multi-agent:
   * Splits ownership
   * Uses reducer to verify consistency
________________


6. Optimize Decomposition (Before Increasing Difficulty)
If multi-agent fails, the issue is usually bad decomposition, not task difficulty.
Bad Decomposition:
   * Agent 1: solve task
   * Agent 2: solve task
Good Decomposition:
   * Agent 1: inspect source files
   * Agent 2: update tests
   * Agent 3: update docs
   * Agent 4: generate manifest
   * Reducer: verify consistency
Key Rule:
   * Assign clear ownership
   * Define expected outputs
   * Avoid duplication of work
________________


7. Handle High Single-Agent Scores Carefully
If single-agent scores > 60% early:
The task is only valid if:
   * Multi-agent ≈ 100%
   * Gap ≥ 23 points
   * OR single-agent requires much longer time
If not:
Fix using:
   * More artifacts
   * Stronger reconciliation
   * Tighter timeout
Or discard the task
________________


8. Prefer Read-Heavy Over Write-Heavy Tasks
Parallelism works best when tasks are:
   * Inspection
   * Classification
   * Extraction
   * Analysis
Parallelism fails when:
   * Multiple agents modify the same output
Best Strategy:
   * Parallelize reading + planning
   * Centralize writing via reducer
________________


9. Source Selection Strategy
Choose datasets that naturally provide shards.
Good Sources:
   * Multi-file codebases (SWE tasks)
   * Contract bundles (legal)
   * Financial reports (finance)
   * Multiple CSV datasets (data analysis)
   * Research paper collections (science)
Avoid:
   * Single-file problems
   * Puzzle-style tasks
   * Sequential reasoning chains
________________


10. Anti-Patterns to Avoid
❌ Difficulty without decomposition
Hard ≠ multi-agent suitable
❌ Vague agent roles
Leads to duplication and confusion
❌ Over-reliance on prompt tricks
Single agents can simulate workflows
❌ Parallel write conflicts
Creates noise, not signal
________________


11. Practical Acceptance Rubric
Use this checklist:
Task Design
   * ≥ 5 independent subproblems
   * Clear reducer logic
   * No hidden merge assumptions
Environment
   * Real artifacts (files, repos, datasets)
   * Not just large prompts
Verification
   * Deterministic or structured
   * Partial scoring supported
Evaluation Flow
   1. Oracle → 1.0
   2. Multi-agent → 0.95–1.0
   3. Single-agent → ≤ 0.72 OR timeout
Retention Criteria
Keep task only if:
   * Gap ≥ 23 points
   * Multi-agent succeeds cleanly
   * Single-agent fails under same budget
________________


Final Principle
The entire strategy can be summarized as:
Break the single-agent with breadth, coverage, reconciliation, and time constraints.
Then make the multi-agent succeed through structured decomposition and strong reduction.
This is the only reliable way to create tasks that remain meaningful even as single-agent models continue to improve.
________________




Managing Time
How to Build Good Tasks Faster and Smarter
________________


1. Purpose of this guide
This guide explains how trainers should:
   * build valid SwarmBench tasks
   * manage time well
   * debug in the correct order
   * improve task quality without wasting runs
   * finish work within AHT
________________


2. What is a valid task?
A task is valid when:
   * multi-agent passes
   * single-agent fails
   * the score gap is 23 points or more
There are two valid ways this can happen.
Valid Type 1: Normal fail vs pass
   * A single agent gets a low score
   * The multi-agent gets a high score
   * The gap is 23+ points
Valid Type 2: Timeout fail vs pass
   * The multi-agent finishes and passes within the time limit
   * The single-agent fails because it times out within the same time limit, so the reward is 0
   * The gap is 23+ points - make sure the multi-agent passes with a 23 point gap.
This is also valid.
Important fairness rule
If a multi-agent system is given 20 minutes, then a single agent must also be given 20 minutes.
Use:
   * same task
   * same evaluation
   * same environment
   * same time budget
Only then is it a fair comparison.
________________


3. Important note about single-agent tool calls
Sometimes trainers may think:
“If a single agent uses many tool calls, maybe the task is no longer valid.”
That is not true.
Even if a single agent uses many tool calls, the task is still valid if:
   * It still fails
   * Or it still times out
   * And multi-agent still passes
   * and the gap is 23+ points
So the rule is not “single-agent must do less work.”
The rule is:
   * A single agent must still fail under the fair setup
   * The multi-agent must still succeed under the same fair setup
   * Making the agents make many calls to tools will also push their context limit, and their accuracy degrades. 
   * For example, we created a task where we asked a single agent to read 16 research papers using a web call tool, but it failed with the same task, multi agent was able to solve it by decomposing it into sub-agents, where each takes care of one research paper.
If a single agent makes many tool calls and still cannot finish, that is still a valid failure.
________________


4. Main rule for trainers
Do not sit idle during agent runs
A single-agent run and a multi-agent run can take a long time.
While they are running, you should already be working on the next task.
Correct working style
Think like this:
   * Task 1 is running
   * You prepare Task 2
   * Task 1 results come back
   * You decide: package it, improve it, or drop it
   * Then Task 2 moves forward
This is how you reduce wasted time and control AHT.
________________


5. Full trainer workflow
Follow this order for every task.
Step 1: Prepare the task
Before running agents, do these first:
   * Choose a good dataset
   * Write the problem statement
   * Write Oracle Solution
   * Write test cases
   * Check if the task really needs decomposition
   * Check if the task is not too easy for one agent
Step 2: Run static and exec checks
Before an expensive agent runs, run the static checks and make sure that all the static checks pass. If there are any failures you should fix them before moving on. .
Step 3: Run draft LLM review first (Optional) 
If you are unsure about the task, before expensive agent runs, run the draft LLM reviewer. If you are pretty sure that your task is good and doesn’t need a draft review you can skip this step. 
This helps catch:
   * weak prompt design
   * unclear instructions
   * low-quality task setup
   * avoidable mistakes
This saves reruns later.
Step 4: Run both agents in parallel
Run:
   * single-agent in one terminal
   * multi-agent in another terminal
Do not wait for one to finish before starting the other unless needed.
Step 5: While runs are happening
Start working on the next task:
   * Find the next dataset
   * Draft the next problem
   * Think about decomposition
   * Prepare the next test cases
Do not waste time watching the terminal.


Step 6: Run the final submission LLM reviewer
Once you have the results and you observed that everything is good then you can proceed with the final QG report. This will run the LLM reviewer and make sure that your task meet the requirements.  


________________


6. Best kind of tasks to choose
The best SwarmBench tasks are not just “hard.”
They should be split-friendly for multi-agent and heavy for single-agent.
Good tasks often have:
   * many files
   * many records
   * many shards or chunks
   * Repeated work across parts
   * a clear merge or synthesis step
   * a need for cross-checking
   * a need for a summary across many sub-results
   * Pushes the agent to do multiple tool calls, which degrades the quality of a single agent. 
These task types are usually better than small tasks with tricky wording.
________________


7. What to do after results come back
There are a few common cases.
________________


Case 1: Single-agent fails, multi-agent passes
This is the best case.
What to do
   * Check that the gap is 23+ points
   * Check that the result is stable
   * package the task
Do not keep changing a task that is already good.
________________


Case 2: Single-agent fails, multi-agent also fails
This means the task idea may still be good, but the multi-agent setup is weak.
First action: check the multi-agent trajectory
your_task_id/execution_logs/multi-kimi-agent/your_task_id/agent/trajectory.json
Look for:
   * where failure starts
   * which sub-agent got confused
   * whether the work split is too large
   * whether the instructions are too vague
   * whether the synthesis step is weak
First fix: improve decomposition.yaml
This should usually be the first fix.
Try to:
   * split the work into smaller parts
   * give each sub-agent a clear job
   * reduce confusion
   * improve the final merge step
   * guide the work without giving the answer
This is usually the fastest way to improve multi-agent performance.
Second fix: improve instruction.md
If decomposition fixes are still not enough, then improve instruction.md.
Do this carefully:
   * add open hints
   * clarify the task
   * remove ambiguity
Do not:
   * give the exact solution
   * make the task too easy
   * help both agents too much
After changes, rerun both agents.
________________


Case 3: Single-agent passes above 70%
This is a danger sign.
But do not stop thinking at:
“This task is bad.”
Your next question should be:
Can this become a timeout task?
This is an important strategy.
If single-agent passes above 70%, think:


Estimate time, you can refer to your multi-agent run logs to see how much time it took, and see how much time the single agent took -if the single agent took more time than the multi-agent, then cap it by adding a timeout in task.toml-
[agent]
timeout_sec = 10
and run the single agent again to see if it fails.
If yes, the task may still be valid.
Timeout strategy
A task is still valid when:
   * multi-agent passes within the time limit
   * single-agent times out in the same time limit
   * gap is 23+ points
This is allowed by the client rule.
Important extra point
Even if the single-agent uses many tool calls, this is still okay.
If it still fails or times out under the same fair time budget, the task is valid.
Good ways to make timeout happen
Use changes like:
   * larger dataset
   * more files
   * more records
   * more chunks
   * more search work
   * more compare work
   * more merge work
   * more synthesis work after parallel steps
These changes help multi-agent because it can split the work.
Bad ways to make timeout happen
Do not use:
   * confusing wording only
   * unclear instructions
   * random noise
   * broken evaluation
   * tricks that make both agents fail equally
If the timeout strategy does not work, then the task is probably not a good fit. Drop it.
Where both agent solves it in the same amount of time. 
________________


Case 4: Both agents pass
This usually means the task is too easy.
What to do
   * do not package it
   * check if the prompt gives away too much
   * check if the dataset is too small
   * check if decomposition is not really needed
   * redesign it or drop it
________________


Case 5: Multi-agent is better, but the gap is below 23
This means the task may be closed, but not ready yet.
What to do
   * improve decomposition
   * increase parallel work
   * increase synthesis burden
   * test again
This is often easier to fix than a task where both agents fail badly.
________________


8. Best order for debugging
When a task is not working, do not change everything at once.
Use this order:
1. Check if the task itself is good
Ask:
   * does this task really need decomposition?
   * can one strong agent solve it alone?
   * is the dataset too easy?
   * is the task naturally parallel?
If the answer is bad here, stop early.
2. Check trajectories
Look at where failure starts and debug based on the single agent trajectory, how it’s able to pass, and the multi-agent trajectory, how it's failing, and improve your task from there.
3. Improve decomposition.yaml
This is usually the safest and fastest fix.
4. Run again
5. Improve instruction.md only if needed
6. Run again
7. If still weak, drop the task
Do not spend too much time trying to save a weak task.
________________


9. Best strategies to reduce AHT
These are the main work habits every trainer should follow.
Strategy 1: Work in pipeline mode
Do not work on only one task from start to finish.
Correct way:
   * one task running
   * one task being prepared
   * one task being reviewed
Strategy 2: Use draft review early
  

Catch obvious problems before expensive runs.
Strategy 3: Fix decomposition before fixing the prompt
This usually improves multi-agent faster and protects the gap better.
Strategy 4: Use a timeout strategy when the single agent is too strong
If single-agent passes, ask:
Can this become a valid timeout task?
Strategy 5: Choose split-friendly tasks
Pick tasks with:
   * many parts
   * repeated work
   * parallel steps
   * strong final merge step
Strategy 6: Do not rerun blindly
Every rerun should have a reason:
   * What failed?
   * What changed?
   * Why should this new run be better?
Strategy 7: Drop weak tasks early
A weak task wastes more time than starting a better one.
Strategy 8: Fair comparison always matters
If using timeout:
   * same task
   * same time budget
   * same scoring
   * same environment
Strategy 9: More tool calls by single-agent do not make the task invalid
If single-agent still fails or times out, it is still a valid failure.
________________


10. Quick decision guide
Use this after each run.
If single-agent fails and multi-agent passes
Package it
If single-agent fails and multi-agent fails
Improve decomposition first
If single-agent passes above 70%
Try timeout strategy next
If both pass
Task is too easy, redesign or drop
If gap is below 23
Improve structure and decomposition, then rerun


________________


11. Things trainers must not do
Do not:
   * sit idle during runs
   * rerun without understanding the failure
   * change prompt and decomposition randomly
   * make the task easier for both agents
   * keep pushing a weak task for too long
   * use unfair timing between single and multi-agent
   * assume many tool calls by single-agent means the task is invalid
________________


12. Final expectation
A good trainer does not only “make a task.”
A good trainer:

Section 5 — Writing instruction.md
instruction.md is the only thing the agent reads. It is the task. Everything the agent does — every file it opens, every decision it makes, every field it writes — is a consequence of what you write here. A weak instruction produces a weak agent response, and a weak response produces a noisy reward signal that cannot be used for training.
This section covers how to write an instruction that is unambiguous, fair, and evaluable.
________________


5.1 — Universal Rules (All Task Types)
Rule 1: Human-authored. No exceptions.
The task prompt must be written by you — a domain expert — not generated by an LLM. An LLM-generated prompt sounds generic, lacks real constraints, and often underspecifies the task in ways that are invisible until agents start producing wrong answers. Reviewers can identify LLM-generated prompts and will reject them.
Rule 2: Give the agent the same briefing a human expert would receive.
Imagine you are handing this task to a brilliant but newly onboarded professional. They are smart, but they do not know your domain defaults. Write the instruction at that level — specific enough to be actionable, not so detailed that you are doing the work for them.
Rule 3: Neither underspecified nor overspecified.
Underspecified
	Overspecified
	Right level
	"Analyze these log files and find issues."
	"In line 8,432 of server-01.log, find the 429 error from IP 192.168.1.1 at 14:32:07."
	"Across all 3 server logs, identify the top 5 slowest endpoints by average response time and any IPs with >50% error rate across 1,000+ requests."
	"Review these vendor reports."
	"On page 4 of Vendor A's report, there is a contradiction with page 7 of Vendor B's report about…"
	"Identify all contradictions between the 10 vendor reports, categorized by domain (financial, technical, security, market)."
	Rule 4: Every constraint your oracle or verifier enforces must appear in the prompt.
If your oracle.json requires verbatim excerpts, the prompt must say so. If your verify.py checks that a specific function returns a specific type, the prompt must specify that function and type. If the agent does not know a rule exists, scoring them on it is a false failure — and false failures corrupt the training signal.
Rule 5: State all file paths and working directories explicitly.
The input files are at:
/input_artifacts/server-01.log
/input_artifacts/server-02.log


Your working directory is /workspace.
Agents should never have to guess where files are.
Rule 6: Do not hint at the answer.
If your oracle answer is "the top 5 slowest endpoints are X, Y, Z…", do not mention X, Y, or Z in the prompt. The prompt should describe the task; the oracle should contain the answer.
________________


5.2 — LLM-Judge Tasks: Output Format Requirement
For verifier_type = "llm-judge", the agent's output goes to /logs/agent/output.json — and your judge.py compares it against oracle.json. This means the output format you specify in the prompt must exactly match the structure of your oracle.
Every key in oracle.json must appear in the output format section of your prompt. Every type must match. If your oracle has "error_rate_pct": 20.77 (a float), your prompt should say "error_rate_pct": <float> — not <int>. If your oracle has nested structures, your prompt must show exactly that nested structure.
The output format block is mandatory at the end of every llm-judge instruction.md:
---


## Output Instructions


Write your final answer to `/logs/agent/output.json` in this exact JSON format:


```json
{
  "field_1": <int>,
  "field_2": <float>,
  "field_3": {
    "sub_field": <str>
  },
  "field_4": [
    {
      "item_key": <str>,
      "item_value": <int>
    }
  ]
}
Do not write anything else to that file.

5.3 — Code-Execution Tasks: Specification Completeness
For verifier_type = "executable", your verify.py defines correctness. If your test expects a specific function, signature, or behavior and the prompt does not specify it, an otherwise correct solution can fail. That is a false failure caused by underspecification.
Everything your verifier checks must be specified in the prompt:
What verify.py checks
	What your prompt must say
	from auth import validate_token
	Fix the validate_token function in auth.py
	validate_token(token, expiry=...)
	The function signature must remain validate_token(token, expiry)
	assert result == True
	The function should return True for valid tokens
	Rules for code-execution prompts:
   1. Name the file explicitly
   2. Name the function if referenced in tests
   3. Specify the interface if required
   4. Name the test for self-verification
   5. State what must NOT be modified
   6. Specify return types if enforced
   7. State the working directory (/testbed)
False failures are treated as trainer errors.

5.4 — RL Training Signal Considerations
This benchmark produces training data for reinforcement learning. The reward signal is only useful when:
   * A capable agent can succeed
   * An incapable agent fails
   * Partial credit reflects real progress
If a prompt causes false failures, capable agents get reward = 0 — bad training signal.
If a prompt is overspecified, weak agents get reward = 1 — also bad signal.
Write prompts where correct work leads to high reward and incorrect work leads to low reward.

5.6 — False Failures: When the Agent Was Right but Scored Zero
A false failure is when the agent produced a correct answer but your verifier rejects it due to prompt gaps.
Common causes and fixes:
   * Field name mismatch → use exact oracle keys
   * Type mismatch → specify <int>, <float>, etc.
   * Sort order ambiguity → explicitly define ordering
   * Floating precision → define rounding rules
   * Case sensitivity → specify lowercase/uppercase rules
   * Structure mismatch → show exact JSON structure
   * Verbatim excerpt ambiguity → define exact length/format
   * ID format mismatch → define format (e.g., PMC123456)
   * Wrong module path → specify exact import path
   * Missing required field → include in output format
Golden rule: If a correct answer can be rejected, fix the prompt so to test this easily make sure to run your multi agent and see if it’s passing 100 percent or not. 
________________


5.7 — Reward Hacking: How Agents Game the Verifier
Reward hacking occurs when agents achieve high scores without solving the task.
Common vulnerabilities:
   * Oracle exposed in input_artifacts/ → agent copies it
   * decomposition.yaml leaks answers → agent skips computation
   * Weak judge prompt → rewards plausibility instead of correctness
   * Keyword checks → agent inserts keywords without solving
   * Round numbers → agent guesses values
   * Placeholder/null values → agent fills structure without content
   * No proof-of-read fields → agent reads partial data
   * Prompt leaks answer → agent infers solution
Design principles to prevent hacking:
   * Include at least one field requiring real input reading
   * Use non-guessable values (precise floats, IDs)
   * Keep oracle.json and verifier only in tests/
   * Ensure decomposition.yaml contains no answers
   * Judge must evaluate field-by-field correctness

tests/verify.py — you write this. Here is a realistic example for a task that asks the agent to fix a discount calculation bug.
The prompt said:
“Fix calculate_discount() in pricing/calculator.py. For account_type='premium', the discount should be 15%, not 20%. For account_type='standard', keep 10%. The function signature is calculate_discount(price, account_type) and must return a float.”
#!/usr/bin/env python3
"""
Verify: calculate_discount() applies correct discount rates.
Every check here corresponds to an explicit requirement in instruction.md.
"""
import sys
import importlib.util
from pathlib import Path


TESTBED = Path("/testbed")
passed = 0
total = 0




def check(name, fn):
    global passed, total
    total += 1
    try:
        fn()
        print(f"  PASS  {name}")
        passed += 1
    except Exception as e:
        print(f"  FAIL  {name}: {e}")




# Import defensively — agent may have put the file in the wrong location
try:
    spec = importlib.util.spec_from_file_location(
        "calculator", TESTBED / "pricing/calculator.py"
    )
    if spec is None:
        print("IMPORT ERROR: pricing/calculator.py not found at /testbed/pricing/calculator.py")
        sys.exit(1)
    module = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(module)
    calc = module.calculate_discount
except Exception as e:
    print(f"IMPORT ERROR: {e}")
    sys.exit(1)


# Check 1: premium account gets 15% (the bug that was reported)
def test_premium_discount():
    result = calc(100.0, account_type="premium")
    assert abs(result - 85.0) < 0.01, \
        f"premium 15% discount: expected 85.0, got {result}"


# Check 2: standard account still gets 10% (regression)
def test_standard_discount():
    result = calc(100.0, account_type="standard")
    assert abs(result - 90.0) < 0.01, \
        f"standard 10% discount: expected 90.0, got {result}"


# Check 3: return type is float (specified in prompt)
def test_return_type():
    result = calc(50.0, account_type="premium")
    assert isinstance(result, float), \
        f"return type must be float, got {type(result).__name__}"


# Check 4: zero price edge case (not undefined behavior)
def test_zero_price():
    result = calc(0.0, account_type="premium")
    assert result == 0.0, \
        f"zero price should return 0.0, got {result}"


check("premium 15% discount", test_premium_discount)
check("standard 10% regression", test_standard_discount)
check("return type is float", test_return_type)
check("zero price edge case", test_zero_price)


print(f"\nResult: {passed}/{total} checks passed")


# Write fractional reward for partial credit
with open("/logs/verifier/reward.txt", "w") as f:
    f.write(str(passed / total))


sys.exit(0 if passed == total else 1)
Rules for writing verify.py:
Rule 1: Every check must trace back to a line in instruction.md.
Before finalizing, read both files side by side. For every check(...) call, find the sentence in the prompt that justifies it. If you cannot find it, remove the check or add the requirement to the prompt.
Rule 2: Import defensively with a clear error message.
If the agent put the file in the wrong location, a bare ImportError tells you nothing. Print the expected path before exiting. This makes test-output.log immediately useful for debugging.
Rule 3: Use abs(result - expected) < tolerance for floats, never ==.
assert result == 85.0 fails for result = 84.99999999 due to floating point precision. Use abs(result - 85.0) < 0.01. Match the tolerance to the precision your prompt specifies.
Rule 4: Test behavior, not implementation.
Do not check how the agent solved it — check that it works correctly. If the agent replaced a function with a class that has a __call__ method, your test should still pass. Test the public interface specified in the prompt.
Rule 5: Include at least one regression check.
The fix must not break existing behavior. If you only check the reported bug, an agent that deletes the function body and hardcodes return 85.0 passes your primary check. A regression check catches it.
Rule 6: Use the partial credit pattern.
The check() helper above lets multiple assertions run independently and writes a fractional reward.txt. This produces a meaningful training signal — an agent that fixes 3 out of 4 requirements scores 0.75, not 0.
Rule 7: Print diagnostics on every check.
PASS premium 15% discount and FAIL standard 10% regression: expected 90.0, got 80.0 makes test-output.log readable by both you and QA reviewers. Silent pass/fail is useless for debugging.
Rule 8: Write reward.txt yourself when using partial credit.
The test.sh template writes reward.txt based on exit_code (1 or 0). If you want fractional scores, write reward.txt inside verify.py directly and always sys.exit(0) so test.sh does not overwrite it with binary 1/0. Or adapt test.sh to not overwrite it.
Where things go wrong:
Agent writes to wrong path.
Agent puts output in /workspace/result.py instead of /testbed/pricing/calculator.py. Your import fails. Prevention: state the exact expected file path in the prompt.
Test assumes installed packages.
verify.py imports pytest or numpy but neither is in the Dockerfile. Test crashes before running any checks. Prevention: test your Dockerfile and verify.py combination before submitting.
Agent modifies tests/.
Agent edits verify.py or deletes its checks to make them pass. Prevention: add to prompt: “Do not modify any files in the tests/ directory.”
reward.txt not written due to crash.
If verify.py raises an unhandled exception outside the check() wrapper, the script exits before writing reward.txt. Harbor sees no reward file and raises RewardFileNotFoundError. Use the check() pattern to wrap all assertions so exceptions are caught.
Test too tightly coupled to implementation.
You check assert hasattr(module, '_internal_cache') — an internal detail never mentioned in the prompt. The agent’s valid implementation does not use caching and fails. Test only what the prompt specifies.
Fixture file missing.
Your test reads a fixture from /testbed/tests/fixtures/config.json but the agent deleted it while refactoring. Your test fails for the wrong reason. Prevention: put fixtures in tests/ (which agents cannot modify) or in input_artifacts/ (baked into Dockerfile).

Important bug:
Shebang on solution/solve.sh
Always write #!/bin/bash (or #!/usr/bin/env bash). Treat any shebang that ends right after env as a critical bug.


How it breaks
When solve.sh starts with #!/bin/env and nothing else, the Linux kernel reads it and exec's /bin/env /solution/solve.sh. With no interpreter argument, env treats the script path as a command and tries to exec it. The kernel reads the same #!/bin/env shebang again. env exec's the script again. This re-exec loop never exits — env repeatedly replaces itself, the process stays alive in state R, and CPU pegs to 100 %. There is no error message because nothing ever fails — each iteration succeeds.


The correct forms terminate the cycle because the kernel passes a real interpreter (bash) as env's argument:


#!/bin/bash — direct interpreter, fastest.
#!/usr/bin/env bash — POSIX-portable; works whether bash is in /bin or /usr/local/bin.
Section 9 — Writing decomposition.yaml
Section 9 — Writing decomposition.yaml
The decomposition guide is the blueprint for multi-agent coordination. It tells the orchestrator how to split the work, what each sub-agent is responsible for, what depends on what, and how results are aggregated. This file is what separates your task from a simple single-agent prompt.
The orchestrator reads this at runtime and uses it to spawn sub-agents. If the decomposition is wrong — too many agents, unclear responsibilities, missing dependencies — the multi-agent run fails even on tasks that are inherently solvable.
________________


9.1 — Structure
sub_tasks:
  - id: unique-short-name
    description: "Exactly what this sub-agent must do, what files to read, what to produce"
    depends_on: []
    parallel_group: map


  - id: another-task
    description: "..."
    depends_on: [unique-short-name]
    parallel_group: reduce
Every sub-task has 4 fields:
   * id — short, unique, descriptive. Used by depends_on references and by the orchestrator in its logs.
   * description — the complete briefing for that sub-agent. Remember: sub-agents run in isolated context. They cannot see each other’s output. They cannot see your instruction.md. Everything they need must be in this description.
   * depends_on — list of sub-task IDs that must complete before this one starts. Empty means it can start immediately.
   * parallel_group — groups that run at the same time. All sub-tasks in the same parallel group run concurrently.
________________


9.2 — Principles of Good Decomposition
Minimal agents, maximum coverage.
Every sub-agent must be necessary. If you can remove a sub-agent and the task is still solvable at the same quality, remove it. Extra agents waste tokens, increase coordination overhead, and slow the run. Reviewers will flag tasks where the sub-agent count is inflated to hit a difficulty target.
Clear, non-overlapping responsibilities.
Each sub-agent should own a distinct piece of work. If two sub-agents both read the same file for the same purpose, one is redundant. If a sub-agent’s description says “assist with” or “help analyse,” it does not have a clear enough role.
Self-contained descriptions.
Sub-agents see only their description. They do not see the main instruction.md, they do not see other sub-agents’ descriptions, and they do not see the overall task goal. If a sub-agent needs to know the expected output format, the file path, or the analysis criteria, put it in the description.
Correct dependency chains.
If reduce depends on all mappers finishing, list every mapper ID in depends_on. If a synthesizer depends on all thread results, list every thread. Missing a dependency means the synthesizer runs before results are available.
Match the coordination pattern.
Map-reduce: all mappers in one parallel group, reducer depends on all mappers.
Fan-out: all threads in one parallel group, synthesizer depends on all threads.
Do not mix patterns within one decomposition unless the task genuinely requires it.

9.3 — Real Example: Fan-Out / Synthesize
Task: survey 11 AI benchmark papers, extract 6 fields per paper.
sub_tasks:
  - id: research-api-bank
    description: >
      Search the web for 'API-Bank (Li et al., 2023)'. Read the full paper.
      Extract: benchmark_name, num_domains, num_tasks, has_human_task_curation,
      has_refusal_ability, has_human_plans. For each field, provide 1-3
      verbatim quotes as evidence. Return structured JSON.
    depends_on: []
    parallel_group: research


  - id: research-acebench
    description: >
      Search the web for 'ACEBench (Chen et al., 2025)'. Read the full paper.
      Extract the same 6 fields with verbatim quote evidence. Return JSON.
    depends_on: []
    parallel_group: research


  - id: cross-validate
    description: >
      Read each research agent's extracted data. For each paper, verify
      benchmark_name matches the actual paper title. Flag any extraction
      where the verbatim quote does not support the claimed value. Produce
      a validated dataset with confidence flags.
    depends_on: [research-api-bank, research-acebench]
    parallel_group: validate


  - id: synthesize
    description: >
      Merge all validated extractions into a single JSON array of 11 objects.
      Resolve any flagged discrepancies. Produce the final output matching
      the required format and write to /logs/agent/output.json.
    depends_on: [cross-validate]
    parallel_group: synthesize
11 research agents + 1 validator + 1 synthesizer = 13 total. Not 23. Not 5. Each agent has exactly one paper, one job, complete context.

9.4 — Real Example: Map-Reduce
Task: security audit across 3 server logs.
sub_tasks:
  - id: map-server-01
    description: >
      Read /input_artifacts/api-server-01.log entirely. For every log entry,
      extract: client IP, HTTP method, endpoint path, status code, bytes,
      response time. Compute: total requests, requests per status code,
      average response time per endpoint, per-IP total and error counts,
      total bytes. Return all metrics as JSON.
    depends_on: []
    parallel_group: map


  - id: map-server-02
    description: >
      Read /input_artifacts/api-server-02.log entirely. Compute the same
      metrics as map-server-01. Return JSON.
    depends_on: []
    parallel_group: map


  - id: map-server-03
    description: >
      Read /input_artifacts/api-server-03.log entirely. Same metrics. JSON.
    depends_on: []
    parallel_group: map


  - id: reduce-aggregate
    description: >
      Take all 3 mapper outputs. Sum status codes across servers. Compute
      weighted average response times per endpoint. Merge IP stats. Sum bytes.
      Identify top 5 slowest endpoints globally, suspicious IPs (>=5 requests
      AND >50% error rate), overall error rate, global avg response time.
      Write final answer to /logs/agent/output.json.
    depends_on: [map-server-01, map-server-02, map-server-03]
    parallel_group: reduce
3 mappers + 1 reducer = 4 total. Clean, minimal, no redundancy.

Step 4: Evaluate the gap.
   * Single and Multi with ≥ 23-point value gap → task is valid. Ship it.
   * Single and Multi with <23 point value gap  → the decomposition needs improvement. Go to Step 5.
Step 5: Debug multi-agent failure.
When multi-agent does not reach a high pass rate, debug systematically. Do not assume the task is unsolvable.
Read execution_logs/multi-kimi-agent/*/agent/trajectory.json to see what the orchestrator actually did.
Common issues:
Issue: Sub-agent received incomplete context.
The orchestrator spawned a sub-agent but did not pass enough information. The sub-agent could not find the file, did not know the output format, or did not know the analysis criteria.
Fix: make the sub-task descriptions in decomposition.yaml more explicit and self-contained.
Issue: Too many sub-agents.
The orchestrator spawned 15 agents when 5 would suffice. Each agent did minimal work, the coordination overhead dominated, and the synthesizer drowned in noisy partial results.
Fix: reduce estimated_sub_agents and merge related sub-tasks.
Issue: Too few sub-agents.
One sub-agent was assigned 500 cases when it should have been split into 5 agents of 100 each. That sub-agent failed for the same reason the single agent fails — context overload.
Fix: split large sub-tasks further.
Issue: Missing dependency.
The reducer ran before all mappers finished, synthesized incomplete data, and scored low.
Fix: verify depends_on lists every prerequisite.
Issue: False failure from the verifier.
Multi-agent produced the correct answer but judge.py scored it low because of a format mismatch, field name difference, or precision issue. This is not a decomposition problem — it is a verifier problem. Read agent/judge_justification.txt to diagnose.
Fix: correct the prompt output format block or the oracle.
Issue: True incapability.
The multi-agent approach genuinely cannot solve the task — the coordination is too complex, the sub-agents hallucinate despite isolated context, or the synthesis step is itself beyond single-agent capacity. This is rare.
Step 6: Re-run and compare.
After each improvement to the decomposition, re-run both single and multi agent. The gap must be at least 38 points on the reward across a single trial run. A 40-point gap is ideal.
________________


9.6 — What Reviewers Check in Your Decomposition
QA reviewers and annotators evaluate decomposition on these criteria. They do not try to derive a better decomposition — they assess whether yours is sound.
Redundancy.
Can any sub-agent be removed without losing coverage? If yes, the task is flagged for rework.
Coverage.
Does every part of the input get processed? If the task has 3 log files and your decomposition only maps 2, that is a gap.
Clear responsibilities.
Can you read one sub-task description and know exactly what it produces, what it reads, and what format it returns? If a sub-task says “help with analysis,” it is too vague.
Necessary dependencies.
Does every depends_on make logical sense? Does the reducer actually need all mapper outputs, or could it start with partial data? Are there unnecessary sequential bottlenecks?
Estimated sub-agent count matches.
If task.toml says estimated_sub_agents = 13, your decomposition.yaml should also contain 13 sub-tasks. If these do not match, one of them is wrong.

Field Definitions
verifier_type — Required
How the agent’s output is evaluated.
Value
	When to use
	llm-judge
	Output is text or JSON graded by an LLM. Used for knowledge, research, and data analysis tasks where there is no single deterministic answer.
	executable
	Output is verified by running tests (for example: code compiles, tests pass). Used for SWE and coding tasks.
	________________


domain — Required
The primary subject area of the task. Pick the closest match.
Value
	Description
	code-swe
	Software engineering, debugging, code generation, repo navigation
	knowledge-research
	Literature review, fact extraction, scientific reasoning, synthesis
	data-analysis
	Processing structured or semi-structured data, statistics, aggregation
	planning-operations
	Multi-step planning, scheduling, resource allocation
	reasoning-math
	Logical reasoning, mathematical problem solving
	________________


coordination_pattern — Required
The multi-agent decomposition strategy this task is designed for.
Value
	Description
	map-reduce
	Split input into shards → parallel processing → aggregate results
	fan-out-synthesize
	Explore multiple independent threads in parallel → synthesize findings
	specialist-routing
	Route sub-tasks to domain specialists → merge outputs
	pipeline
	Sequential stages where each stage feeds the next
	hierarchical
	Tree of manager agents delegating to specialist sub-agents
	debate
	Multiple independent agents solve the same problem → consensus
	________________


human_solving_hours_estimate — Required
Estimated hours for a human domain expert to solve this task from scratch, without AI assistance.
This is the primary difficulty signal aligned with client requirements:
Hours
	Difficulty
	10 – 99
	Medium
	100+
	Hard
	Rules:
   * Be conservative — estimate for a knowledgeable human, not a novice
   * Must be justified by the nature of the task (data volume, reasoning depth, number of sources)
   * Not automatable by simple scripts or keyword matching
Examples:
   * Reading and clinically analyzing 1500 medical case files → 120.0 (Hard)
   * Cross-referencing 10 vendor reports across 4 domains → 14.0 (Medium)
   * Synthesizing findings from 11 research papers → 32.0 (Medium)
________________


human_solving_hours_justification — Required
A sentence or two explaining how you arrived at human_solving_hours_estimate. Break down the work: reading time + analysis time + synthesis time.
Example:
“Requires reading all 10 vendor reports (~33K tokens), manually tracking contradictions across 4 domains, and producing a structured report. ~2h per domain (8h total) + ~6h for synthesis and verification.”
This field is used by QA reviewers to validate the difficulty rating. Tasks where the justification does not support the hours estimate will be flagged for revision.
________________


reference_link — Required
A URL pointing to the source of the task. This gives reviewers and future trainers context for where the task came from.
For knowledge and research tasks: link to the paper, dataset, or report the task is based on.
For data analysis tasks: link to the data source or a relevant real-world system.
For SWE tasks: link to the GitHub issue or PR the task is derived from.
# Research task
reference_link = "https://arxiv.org/abs/2310.12123"


# SWE task from a real GitHub issue
reference_link = "https://github.com/django/django/issues/12345"


# Data analysis from a public dataset
reference_link = "https://www.kaggle.com/datasets/some-dataset"
IMPORTANT — reference_link Must Be Accurate and Verifiable


The reference_link field in [metadata] must contain the actual, valid URL(s) that you used as the source or basis for your task. This is not a throwaway field.


Do:


   * Use the real GitHub PR/issue URL if your task is based on a code change (e.g., https://github.com/pydantic/pydantic-ai/pull/468)
   * Use the real arXiv listing page if your task is research-based (e.g., https://arxiv.org/list/cs.LG/2025)
   * Use the real dataset URL if your task uses a public dataset
   * Include multiple URLs separated by commas if your task draws from multiple sources


Do NOT:


   * Use placeholder or generic URLs (e.g., https://example.com or https://github.com)
   * Use URLs that do not actually relate to your task content
   * Leave this field empty or use a dummy value


Reviewers verify that the reference_link points to a real, accessible source that matches the task content. A faulty or placeholder reference link will result in rework.

estimated_sub_agents — Required
The number of sub-agents the multi-agent solution is expected to spawn. Used to inject ${ESTIMATED_SUB_AGENTS} into the coordination prompt at runtime.
Set this to the number of agents in your gold decomposition.

input_token_estimate — Required
Approximate total tokens in all input artifacts (files the agent must read). Used to verify context pressure — this is why multi-agent is necessary.
Calculate as:
total file sizes in bytes ÷ 4
This is a rough token estimate.

why_multi_agent — Required
A clear, specific explanation of:
   1. Why a single agent fails on this task
   2. What specifically breaks (context overload, attention degradation, confusion, etc.)
   3. How multi-agent decomposition solves it
This must be specific. Do not write generic statements like “it’s too complex for one agent.” Quantify where possible using token counts, number of documents, or number of comparisons.
Good example:
“Three domain databases (~500K tokens total) require clinical reasoning on 1500 cases. Single agent context overflows, causing truncated reads and hallucinated PMCIDs. 15 chunk-reader sub-agents (5 per domain, ~33K tokens each) process within manageable windows, 3 domain synthesizers merge, and 1 final synthesizer diagnoses.”
Bad example:
“This task is too large for a single agent.”

Mistake 3: Using the Wrong Trial and Gap Criteria


We have identified that some tasks are being judged against the wrong scoring targets, which leads to unnecessary rework and weak task design decisions. Please review the following to avoid invalid evaluations.
Root Cause
A common mistake is optimizing around arbitrary thresholds such as “single-agent must be below 0.3” and “multi-agent must be above 0.7.” That is not the key requirement. The more important standard is an absolute gap of at least 0.23 between single-agent and multi-agent performance. Another issue is failing to run the required trajectories consistently. In addition, when a task requires changes across 30+ files but only produces a 0.2 gap, that usually indicates the task framing or subagent setup needs improvement.
Required Fix
Run one single-agent trial and one multi-agent trial for every task. Evaluate the task based on whether it achieves a gap of >= 0.23, not whether it hits a specific low/high score pair. For example, 0.5 single-agent vs 0.9 multi-agent is still acceptable because the 0.40 gap is present. If the gap is too small, revise the task framing, instruction clarity, or decomposition structure.
Action Items for All Trainers:
         * Run Both Required Trajectories: One single-agent trial and one multi-agent trial for each task.
         * Focus on the Gap: Prioritize a 0.23+ gap over arbitrary target scores.
         * Revisit Weak Gaps: If a large task produces only a small separation, improve the task structure rather than forcing the numbers.

Mistake 4: Instruction.md and Verifier Requirements Do Not Match (foir executable tasks)
We have identified that some otherwise valid solutions are being rejected because the verifier is enforcing requirements that are not clearly surfaced in instruction.md. Please review the following to prevent false negatives.
Root Cause
This happens when the verifier expects a specific identifier, path, function name, file, or configuration choice that the instruction does not clearly communicate. For example, if the verifier checks for a particular setting or file path but the prompt only gives a vague description, a correct implementation can still score zero simply because it used a different name or location.
Required Fix
Phrase the problem clearly in instruction.md and make sure any verifier-critical names, files, or paths are discoverable from the task instructions. This does not mean every implementation detail must be spelled out verbatim, but any requirement the verifier strictly enforces must be communicated clearly enough that a correct agent can satisfy it.
🚨 The Core Issue: Hidden Requirements Create False Failures
If the verifier is stricter than the instruction, then the task is not measuring problem solving fairly. The agent should not have to guess hidden naming conventions or invisible file expectations.
Action Items for All Trainers:
         * Align Prompt and Verifier: Make sure the instruction and verifier are testing the same outcome.
         * Name Critical Files Clearly: If a specific file or path matters, surface it in the task.
         * Remove Hidden Constraints: Do not enforce requirements the prompt never made visible.

Mistake 5: Decomposition Describes HOW Instead of WHAT


We have identified that some decomposition.yaml files are written like implementation scripts instead of work-division plans. Please review the following to avoid unfair task setups and poor multi-agent behavior.
Root Cause
This issue occurs when decomposition descriptions include exact code strings, precise attribute names, function signatures, or line-by-line implementation steps. That turns the decomposition into a coded answer key instead of a high-level division of work. It also gives multi-agent runs an artificial advantage and weakens the quality of the task. In many cases, poor subagent design is also the reason a large task still shows only a small score gap.
Required Fix
Your decomposition should describe what each subagent must accomplish, not how to implement it. Keep the descriptions outcome-oriented and scoped around meaningful workstreams. Avoid exact code snippets, exact attribute names, and implementation-level instructions. When possible, prefer the map-reduce and fan-out-synthesize coordination patterns rather than weaker alternatives.
🚨 The Core Issue: Decomposition Is for Work Division, Not Code Authoring
A good decomposition tells each subagent which part of the problem space it owns. It should not hand out the exact implementation recipe.
Action Items for All Trainers:
         * Describe Deliverables, Not Code: Focus on goals and ownership boundaries.
         * Avoid Exact Implementation Cues: Do not include exact strings, exact names, or line-by-line edits.
         * Use Strong Coordination Patterns: Stick to map-reduce and fan-out-synthesize unless there is a compelling reason not to.
         * Re-scope Weak Tasks: If a 30+ file task only produces a small gap, redesign the subagent breakdown.

Mistake7: Git History Leaks the Answer (executable and code-swe only tasks)
We have identified that some tasks unintentionally expose the solution because the repository history is left intact. Please review the following to prevent answer leakage.
Root Cause
If you clone a repository with full git history, the agent can inspect prior commits, locate the original PR, and potentially cherry-pick the answer directly. This is especially risky when the task is based on a real upstream change.
Required Fix
Restrict history whenever possible, and remove git metadata after checking out the required state. At minimum, use:
git clone <repo_url> repo
git checkout <commit_hash>
rm -rf .git
Where appropriate, --depth 1 can also help reduce exposure.
🚨 The Core Issue: Repository History Can Reveal the Gold Answer
If the agent can browse commit history freely, the task stops measuring reasoning and starts measuring lookup.
Action Items for All Trainers:
         * Limit History Exposure: Use shallow cloning when possible.
         * Remove .git After Checkout: Do not leave commit history inside the task environment.
         * Audit for Leakage: Assume the agent will inspect anything you leave accessible.

Mistake 8: Verification Relies Too Heavily on Substring Matching


We have identified that some verifiers are awarding too much weight to static text checks instead of real behavioral validation. Please review the following to make your tasks robust.
Root Cause
Checks such as “does this file contain import zoneinfo” or “does this string appear in source” are easy to game. An agent can insert dead code or irrelevant text and still pass. When most of the verifier weight comes from substring checks, the task no longer measures whether the implementation actually works.
Required Fix
Make sure a substantial share of verifier weight comes from real execution, such as running a test suite or exercising the changed behavior directly. As a rule of thumb, aim for 50% or more of verifier weight to come from behavioral or functional testing. Use pattern checks only as light support, not as the foundation of the verifier.
Action Items for All Trainers:
         * Prioritize Behavioral Validation: Use test runs or functional execution whenever possible.
         * Use Pattern Checks Sparingly: Reserve them for lightweight guardrails, not primary scoring.
         * Check for Dead-Code Passes: Ask whether a non-working solution could still pass your verifier.

Action Items for All Trainers:

         * Pin Python Dependencies: Do not leave pip packages unversioned.
         * Protect Reproducibility: The environment should behave the same across repeated task runs.

Avoiding Similarity on instruction.md
Structurally Identical Tasks Get Flagged by the Similarity Checker
We have identified that some trainers are producing multiple tasks that, despite having different subject matter, share an almost identical document structure. The client's similarity checker flags these tasks even when the underlying content is different. This results in rework. Please review the following to understand why this happens and how to avoid it.
Root Cause
The similarity checker does not only compare raw content — it also detects structural similarity across tasks. If two tasks follow the same template (same section ordering, same sentence patterns, same field layouts), they will be flagged as near-duplicates even if they cover completely different topics.


Real example of what gets flagged:


Two research tasks were submitted by the same trainer. One covered quantitative biology papers, the other covered machine learning papers. The content (papers, questions, answers) was entirely different. However, the similarity checker flagged them because:


         1. Identical instruction.md structure:


         * Both opened with the same sentence pattern: "Read thirty-nine real arXiv [domain] papers (~NNK tokens, N.Nx context) from /input_artifacts/papers/ and write one JSON report to /logs/agent/output.json..."
         * Both listed papers in the same code-block format
         * Both had the same section ordering: Output shape -> Per-paper fields -> Per-paper body-specific questions -> Aggregations -> Grading -> Working directory
         * Both used the same phrasing for the grading section with only tolerance numbers changed


         2. Identical decomposition.yaml pattern:


         * Both used exactly 19 specialist sub-agents (A through S) + 1 synth/reducer
         * Each specialist had the same description template with only paper IDs and questions swapped
         * The synth/reducer task had the same boilerplate text


         3. Identical task.toml template:


         * human_solving_hours_justification followed the exact same sentence structure: "A senior [domain] researcher working through the dataset unaided: initial per-paper body read... - 39 papers x N.Nh = NNh. Locating the two body-specific paper answers... - 78 Qs x NN min = NN.Nh..." with only numbers changed
         * why_multi_agent used the same paragraph structure with only token counts and domain words changed
Why This Matters
Even though both tasks were valid, well-constructed, and had genuinely different content, the similarity checker saw them as the same task produced from a template. When the client reviews a delivery batch and finds structurally identical tasks, it raises concerns about:


         * AI-generated content (the uniform structure feels synthetic)
         * Low effort / copy-paste task creation
         * Inflated task count without genuine variety


This can result in batch-level rejections, not just individual task rework.
Required Fix — How to Keep Your Tasks Structurally Different
If you are creating multiple tasks in the same domain or using a similar approach, you must vary the structure across tasks. Here is how:


1. Vary the instruction.md layout:


         * Do NOT reuse the same section ordering across tasks. If Task A goes: Context -> Output Format -> Questions -> Grading, then Task B should go: Scenario Background -> Deliverables -> Evaluation Criteria -> Detailed Requirements, or some other ordering.
         * Change the opening paragraph style. Do not start every instruction with the same sentence pattern.
         * Use different heading styles (numbered sections vs. named sections vs. hierarchical sub-sections).
         * Vary how you present the list of input files (inline list vs. table vs. grouped by category vs. described in prose).


2. Vary the decomposition strategy:


         * Do NOT use the same number of sub-agents for every task.
         * Change the grouping logic. If Task A assigns 2 papers per specialist, Task B could assign papers by topic cluster, or by methodology type, or by publication date range.
         * Use different sub-agent naming conventions (specialist-A/B/C vs. topic-based names like genomics-reader, imaging-reader vs. numbered agents).
         * Vary the reducer/synthesizer role — in one task the reducer might compute aggregations; in another, it might produce a narrative summary.


3. Vary the task.toml justifications:


         * Write the human_solving_hours_justification in a different structure each time. One task could use a bullet-point breakdown, another could use a narrative paragraph, another could break it into phases (setup, execution, QA).
         * Write the why_multi_agent explanation with different framing. One task could lead with the context overflow argument, another could lead with the parallelization benefit, another could focus on the coordination requirement.


4. Vary the output format:


         * Do not use the same JSON schema across tasks. Change field names, nesting structure, or output organization.
         * If one task uses {"papers": [...], "aggregations": {...}}, the next could use {"results": {"per_item": [...], "summary": {...}}} or a flat list, or separate output files.


5. General rule: If you can diff two instruction.md files and the diff is mostly just domain words and numbers swapped out, the tasks are too similar.
Action Items for All Trainers
         * Treat each task as a standalone design. Do not start from a previous task and find-replace domain terms.
         * Review your own submissions for structural overlap before uploading. Open two of your instruction.md files side by side — if the structure is recognizably the same, rewrite one.
         * Vary at least 3 of the 5 structural dimensions above between any two tasks you submit.
         * Do not use AI to generate multiple instruction.md files from the same prompt template. This is the fastest way to get flagged.

## How Harbor Executes a Task
1. **BUILD** — Docker image built from `environment/Dockerfile`. Input files baked in.
2. **START** — Container started. `/logs/agent/` and `/logs/verifier/` are volume-mounted to the host.
3. **AGENT SETUP** — kimi-cli installed inside the running container.
4. **AGENT RUN** — Agent receives `instruction.md` content and works inside the container.
   - Single agent: tool-restricted, no Task/CreateSubagent tools available.
   - Multi agent: reads decomposition.yaml, has full tool access including sub-agent spawning.
5. **VERIFICATION** — Harbor copies `tests/` into container at `/tests/`, runs `test.sh`.
   - For llm-judge: `test.sh` → `judge.py` → calls LLM → writes `/logs/verifier/reward.json`
   - For executable: `test.sh` → `verify.py` → runs tests → writes `/logs/verifier/reward.txt`
6. **CLEANUP** — Container destroyed. All results in `execution_logs/` on host.
## Critical Rules
- The agent NEVER sees `tests/`, `solution/`, or `decomposition.yaml` during execution. Harbor uploads `tests/` only AFTER the agent finishes (Phase 5).
- Files written to `/logs/agent/` inside the container appear on the host automatically (volume mount).
- `reward.txt` contains "1" or "0". `reward.json` contains `{"reward": 0.75}` (float 0.0-1.0).
- Oracle agent runs `solution/solve.sh` instead of kimi — no LLM, just bash. Must score 1.0.
## Two Verifier Types
- `llm-judge`: Agent writes JSON answer → judge.py scores field-by-field against oracle.json → 0.0-1.0
- `executable`: Agent modifies code → verify.py runs tests → 1 (pass) or 0 (fail)

- `swarm-kimi-multi`: Kimi with ALL tools. Reads decomposition.yaml. Spawns sub-agents.
Both receive the SAME `instruction.md`. The gap between their scores is what the benchmark measures.

## PYDANTIC VALIDATION CONTRACT — READ CAREFULLY
This JSON is parsed by Pydantic models (`QualityGateReport` → `LLMReview` → `QDResult` → `CheckDetail`, plus `Decision` and `CheckResult` enums). ANY deviation from the rules below raises a `ValidationError` and the **entire review aborts** with a message like `'<value>' is not a valid CheckResult` or `Input should be a valid integer`. You will not get a second chance — obey this contract exactly.
### Enum values — case-sensitive, no synonyms allowed
| Field | Allowed values (exactly these strings, nothing else) |
|---|---|
| `decision` | `APPROVE`, `REJECT`, `MANUAL_REVIEW` |
| `dimensions.*.result` | `PASS`, `FAIL`, `NOT_APPLICABLE`, `WARN` |
| `dimensions.*.checks[*].result` | `PASS`, `FAIL`, `NOT_APPLICABLE`, `WARN` |
**FORBIDDEN variants that will crash the parser** (do NOT emit any of these for a `result` field):
`N/A`, `NA`, `n/a`, `Not Applicable`, `not_applicable`, `Passed`, `passed`, `pass`, `Failed`, `failed`, `fail`, `Warning`, `warn`, `OK`, `Ok`, `SKIP`, `Skipped`, `NONE`, `null`, `""`, numbers, booleans.
Use `NOT_APPLICABLE` (uppercase, underscored) for not-applicable. Use `WARN` (not `WARNING`).
**FORBIDDEN variants for `decision`**: `Approve`, `approve`, `Reject`, `reject`, `MANUAL`, `Manual_Review`, `manual_review`, `NEEDS_REVIEW`, `PENDING`. Use exact uppercase `APPROVE` / `REJECT` / `MANUAL_REVIEW`.
### Type constraints
| Field | Required JSON type |
|---|---|
| `task_id` | string |
| `decision` | string (one of the enum values above) |
| `dimensions` | object (map of dimension name → object) |
| `dimensions.*.result` | string (CheckResult enum) |
| `dimensions.*.checks` | array of objects |
| `dimensions.*.checks[*].id` | **integer** — NOT a string. `1` is valid; `"1"` is rejected. |
| `dimensions.*.checks[*].name` | string (non-null) |
| `dimensions.*.checks[*].result` | string (CheckResult enum) |
| `dimensions.*.checks[*].reason` | string (non-null; use `""` if empty, never `null`) |
| `dimensions.*.justification` | string (non-null; use `""` if empty, never `null`) |
| `rejection_reasons` | array of objects |
| `rejection_reasons[*].code` | string (non-null) |
| `rejection_reasons[*].message` | string (non-null) |
### Structural rules
- Emit strictly valid JSON: no trailing commas, no comments, no `// …`, no smart quotes (`""`/`''`), no Python `None`/`True`/`False` — use `null`/`true`/`false` only where allowed, and per the table above `null` is NOT allowed for any field in this schema.
- Every QD listed in `dimensions` MUST have all three keys (`result`, `checks`, `justification`).
- Every entry in `dimensions.*.checks` MUST have all four keys (`id`, `name`, `result`, `reason`).
- Every entry in `rejection_reasons` MUST have both keys (`code`, `message`).
