Batch-12 — Feedback for Turing


Delivery: delivery-harbor-format-samples-12-2026-07-28 · 12 samples · SwarmBench V2 (OpenCode harness)


This document gives our feedback on the 12 samples in this delivery. Overall the batch is strong; the graders are grounded and we found no reward-hacking on either arm in any sample. The notes below are about how the score is composed, how hard the tasks are, and label/provenance accuracy — not about bad work.


───────────────────────────────────────
How to read this document (key terms)


Each sample is an agent task with an automatic grader. A few terms used throughout:


* The task — an instruction plus input files; the agent must produce one or more deliverable files (a report, a spreadsheet, a slide deck, etc.).
* SA and MA — every task is attempted two ways: SA = single agent (one agent working alone) and MA = multi-agent (a coordinated "swarm" of agents). Both run the same task, same inputs, same time budget, and normally the same underlying model — the only intended difference is one agent vs many. The point is to measure how much the multi-agent approach helps, shown as the gap between the MA score and the SA score. Each score is a number from 0 to 1.
* Verifier / grader (verify.py) — the program that reads the agent's output files and computes the score. It is shipped with each sample.
* verifier_type — a label in the sample's config declaring how the grader works. Three possible values:
* deterministic / executable — pure code, no AI. Scores by fixed rules (exact text matches, arithmetic, comparison to a known answer key). Same input always gives the same score.
* llm-judge — an AI model reads the output and rates its quality.
* hybrid — a mix of both: some checks are plain code, others use an AI judge.
* LLM judge — when a grader uses an AI model to rate quality. "Cross-family" means the judge is a different model from the one being tested, which avoids a model grading its own work.
* Ground truth (GT) / frozen oracle / frozen corpus — the fixed reference material the grader checks answers against (e.g. the real source documents, or a hand-verified answer key). "Frozen" means the agent cannot see or change it.
* Structural check vs content check — a structural check asks "is the output the right shape?" (file exists, valid schema, right number of rows, an id copied over from an input file). A content check asks "is the work actually right?" — either an AI judge rating quality (rubric) or a comparison against ground truth (GT). Throughout this document content = rubric + GT.
* Freebie floor — the score an empty-but-well-formatted submission can collect for free from structural checks alone, without doing any real work. Lower is better.
* Completion cliff — when an arm scored low because it produced nothing (e.g. it ran out of budget before writing any file), rather than because its work was poor quality. A "wrote-everything vs wrote-nothing" gap is not a clean measure of quality.
* Fail-closed / fail-soft — what a grader does if its AI judge can't be reached: fail-closed = give that check a 0 (penalizes the agent, never inflates); fail-soft/drop = skip the check. Both have trade-offs noted below.
* decomposition.yaml — the pre-written orchestration plan shipped with each sample: a list of sub-tasks, each naming a role, its input files and its output path.
───────────────────────────────────────
Overall assessment


Most graders in this batch are well grounded — frozen source documents, hand-verified answer keys, or figures recomputed from the source — and where an AI judge is used it is cross-family (no model grading itself). The graders correctly give near-zero scores to empty or copy-pasted submissions, so the low-scoring arms genuinely earned their low scores. The exception worth naming up front is how much of that ground truth is genuinely held out: in several samples the values the grader checks are already sitting in the agent's input files (see A4).


What we're asking for, and where it applies. Two of the asks below are delivery-wide and neither needs any sample regenerated: (1) add a realistic high-level task description as an extra file per sample, and (2) report the content and structural scores separately alongside the overall score. Everything else is scoped to named samples. Going forward we'd also like content to make up at least 40% of every grader's score. The full list is at the end.


Our main feedback is on how the reward is composed. In several samples a well-formed but hollow submission can bank a large fraction of the score from structural checks alone, which lifts the multi-agent score without reflecting extra work. To be explicit: we do not read this as the model gaming the grader. The agent is doing what the instruction asks; where the instruction and the rubric only specify the shape of the output, a correctly-behaving agent will produce the right shape and stop there. The fix is on the specification side — weight substance, not shape.

A2. What the score is made of — and why we'd like to see it split.


The blended reward is doing two jobs at once: it reports whether the output has the right shape, and whether the work is right. Those two move independently — a multi-agent run reliably produces well-formed files, so the shape half tends to sit near the top of its range while the content half is what actually separates a good run from a poor one.


We tried to separate the two ourselves, and mostly couldn't. Only some samples ship per-check scores; several of those don't label their judged checks; and two (GLEN-HELEN, CROSS-COUNTY-BOND) ship no per-check breakdown at all. The one sample we could fully reconstruct — IETF-RFC — shows why it's worth having: the multi-agent run scored 0.948 on structure against 0.845 on content, and the single-agent run 0.497 against 0.599. Both reconcile exactly to the reported 0.900 and 0.544, and both say far more about the two runs than the blended numbers do. Note the single-agent arm actually scored higher on content than on structure — which the blended 0.544 completely hides.


So we'd like two things, and they work together:


1. Report the split. Emit content_score (rubric + GT checks) and structural_score (presence / schema / format / roster-copy checks) as separate fields alongside the blended reward, so a run's real result is legible without re-deriving it.
2. Change what the blend is made of on the samples flagged in A3 below, where the structural share is large enough that the blended number is mostly reporting shape.
Scope: the reporting split (1) applies to all samples — it needs the scoring re-run, but no samples regenerated. The reweight (2) applies only to the samples named in A3. Together these are the most useful change in this document.

One clarification on that 40%. It means rubric and ground truth together. A rule of "≥40% must be LLM-rubric" would wrongly penalise your best graders: GLEN-HELEN has no LLM rubric at all and is 95% ground truth, and that is exactly what a strong deterministic grader looks like. Rubric and GT should be counted together as content, with GT preferred wherever it is feasible.


Reweight targets in this batch, in priority order: IETF-RFC (~60% floor), NASA (~55%), CROSS-COUNTY-BOND (~39%), RURAL-TELEHEALTH (~30%). TARIFF also sits at ~35%, but its floor comes from spoon-fed ground truth rather than structural padding, so it belongs under A4 rather than here.


These are picked by freebie floor, not by the 40% rule — the two catch different things. IETF-RFC (47% content) and RURAL-TELEHEALTH (66%) both clear 40% on check counts, yet a hollow submission still banks ~60% and ~30% of their score. NASA fails on both counts and is the clearest single fix in the batch.


‡ A note on reading this table. We bucketed every check by reading verify.py, not by trusting the manifest labels. Most graders average all their checks equally, so a check count is also a weight — with two exceptions, both marked ‡ above:


* GLEN-HELEN weights its 6 compliance checks at 25% of the score and its other 67 at 75%, so a compliance check is worth roughly 4× any other — while the manifest declares all 73 equal.
* 911-COMMISSION scores a single judge function averaged over 13 chapters. Of its 5 declared checks, three are that same function listed three times, one is a pass/fail gate rather than a scored term, and one is weight: 0 and never reaches the score.
Please make the manifest weights match the real formula in both.


One further caveat. In the _eligible-gated family (WORLD-BANK, US-VETERANS, WIKIDATA) the deterministic checks only score for records the judge has already approved, so the judge's real influence is greater than the rubric column suggests. Bucketing a handful of consistency/anti-gaming checks is a judgement call either way — happy to share our per-check classification if you'd like to review any of it.


Note that a structural check is not automatically a freebie. WORLD-BANK and US-VETERANS are ~37–38% structural but have ~0% floors, because every check sits behind the _eligible gate below. That gating is the good pattern.


Three patterns already used in this batch hold the floor at or near zero — we'd like to see them standardised:


1. An _eligible authorship gate — every per-record check is gated behind a deterministic authorship test (copy-density, word-order, source vocabulary) plus judge verdicts on whether the record is composed/specific/deep. A hollow or copied record then earns nothing on any check. Used well in WORLD-BANK, US-VETERANS, WIKIDATA, RECOVERY.
2. Ground truth denominated over the whole corpus — checks are per-item shares over the fixed corpus requiring exact matches against frozen truth. Used well in GLEN-HELEN.
3. Score only the artifacts, and count a missing one as 0 inside the mean — FINANCE does this well: the presence check doesn't earn credit, it sets the denominator of the content grade, and the structural checks are diagnostics that never enter the reward. Nothing is bankable without producing gradeable work.
A4. Where full ground truth is infeasible, hand-verify a subset and give it real weight.


Several graders credit values that are already sitting in the agent's input files, so the check confirms the agent read a provided file rather than that it did the research: CROSS-COUNTY-BOND (10 of 11 answer-key entries are in county_context; only 1 is genuinely external), NASA (roster copy; only 1 true held-out fact), IETF-RFC (rfc_index.csv is provided).


We understand that a complete answer key is sometimes prohibitively expensive to build. We are not asking for full coverage — a small, hand-verified, held-out slice (a handful of rows or entities that are not in the inputs), carrying meaningful weight, is worth far more than a large key that the agent was handed. Please add a few genuinely external entries to the samples above rather than expanding the spoon-fed ones.


A5. Task calibration — please leave headroom at the top.


7 of the 12 multi-agent runs scored ≥0.80: RECOVERY 0.91, IETF 0.90, FINANCE 0.88, GLEN-HELEN 0.85, WORLD-BANK 0.85, WIKIDATA 0.82, NASA 0.82. We'd like the strongest MA run on a task to land nearer 0.70–0.80, so the task still discriminates between a good run and an excellent one.


To be clear: this is about the MA ceiling, not the gap. A large SA→MA gap is fine and is what we want to see — the concern is a task on which the multi-agent arm is already at 85–95%, which leaves nothing to measure as models improve.


There are two different causes here, with two different fixes:


* Score composition — NASA (0.82) and IETF (0.90) sit on 55–60% freebie floors, so the fix is the reweight in A2/A3.
* Task difficulty — RECOVERY (0.91), GLEN-HELEN (0.85), WORLD-BANK (0.85), WIKIDATA (0.83) have low floors and tight graders, so those scores are legitimately earned. There the fix is to make the task harder: more items, more decoys, more held-out truth, tighter tolerances.
B. Labels and provenance


B1. verifier_type — two missing, eight imprecise, two correct. We checked each declared label against whether verify.py actually calls a model:


* Missing (2): IETF-RFC and NASA declare no verifier_type at all, though both graders call a judge. Please add one (hybrid fits both).
* Imprecise (8): WIKIDATA, RECOVERY-TRIAL, FINANCE, US-VETERANS, WORLD-BANK, 911-COMMISSION, TARIFF and RURAL-TELEHEALTH declare llm-judge and do call a judge, so the label isn't false — but in several the plain-code half carries most of the score (TARIFF uses a judge on only 3 of its 31 checks). hybrid would describe those better. Low priority.
* Correct (2): GLEN-HELEN and CROSS-COUNTY-BOND declare executable and contain no model call anywhere — no change needed.
None of this changes a score; the label is what tooling and the team use to catalog the tasks and to know which ones need an AI judge available at grade/train time.


B2. The models are non-standard third-party deployments and aren't clearly documented.


The agent models are non-standard third-party Kimi deployments: most samples ran on kimi-k2p6, RECOVERY-TRIAL on kimi-k2p7-code, and two samples (WORLD-BANK, CROSS-COUNTY-BOND) on an opaque personal model deployment (accounts/bhanu-nalamadgu-7pl5/deployments/ut1aj6qu) rather than a standard named model. Please record the model used by each arm in the delivered metadata, and confirm what that custom deployment maps to.


There is also one more serious version of this in NASA (S11): there, the two arms ran on different models — the single-agent run used kimi-k2p7-code and the multi-agent run used kimi-k2p6. Because SA and MA are supposed to differ only in single-vs-multi agent, running them on different models muddies the comparison. (In NASA's specific case it happens to be harmless — see that sample below — but it should be confirmed and the record fixed.)
