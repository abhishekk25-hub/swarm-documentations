Potential Issues
* Task is trivially automatable. The parse_log_stats tool returns exact JSON statistics (status counts, endpoint averages, IP stats, total bytes). A human with Python/awk solves this in 1-2 hours, not the required 10+.  
* Synthetic data is too clean. All entries follow identical format: 
   * [timestamp] IP METHOD /path STATUS bytes ms. 
   * No multi-line entries, no missing fields, no encoding issues, no noise. Real server logs are much messier. [Extending — 03/17 feedback: "can we find real + more complex logs?"]
Sample 2: Synthetic Security Audit (BENCH-MAPREDUCE-SEC-001)
Issues
* Phase 3 (blind) outperformed Phase 2A (multi-agent gold) (86 vs 72). Root cause identified: the gold plan's ReportAggregator agent consumed 36k tokens but dropped function-level precision during synthesis (16/24 function names preserved vs Phase 3's 23/24). The aggregation step itself is losing information.  
* No per-sub-task rubric. Rubric is at the final report level only. Guidelines ask for partial credit per sub-task.  
* Pass threshold too low. At 65/100, the single agent (61) nearly passes. A higher threshold (e.g., 75) would create a clearer pass/fail distinction. Counterintuitively, the single agent classified severities BETTER than the multi-agent (72% vs 32% accuracy) — the multi-agent auditors each made up their own severity scales that didn't align with gold.  
* Artificially uniform vulnerability distribution. Exactly 3 vulnerabilities per module (8 × 3 = 24). Real codebases have uneven distribution — some modules have many issues, others are clean. This makes it feel synthetic.

Token Analysis Definitions
Input Tokens: 
This is the size of the input data the task provides (from input_token_estimate in task.toml) -  how much text the agent needs to read. For reference, Kimi K2.5's context window is ~262K tokens. Samples above 262K cannot be fully read by a single agent in one pass. This is different from the total tokens consumed during execution, which includes system prompts, tool calls, re-reads, and agent reasoning. For example, QBio Paper DB has 600K input tokens but the single agent consumed 1.55M total tokens (due to re-reads and overhead), while multi-agent consumed 1.1M total tokens across orchestrator and 19 workers (each worker reads just 2-3 papers in focused context, critical path only 240K).


SA Total:
Everything the single agent read and wrote (prompt + completion tokens). Full cost of the SA run. This includes re-reads of input (and not just one read of the input). 
Example (QBio): 1.55M prompt + 9K completion = 1.6M.
SA Out:
Just what SA wrote (completion tokens only). Much smaller than SA Total because reading dominates. 
Example (QBio): 9K — SA mostly reads papers, barely writes.
MA Total:
Orchestrator + sum of all sub-agents (prompt + completion). Total compute cost — what you would pay on an API bill. 
Example (QBio): orch 150K + 19 sub-agents 948K = 1.1M.
MA Out
Orchestrator output + sum of all sub-agent outputs. Total text/code generated across the whole system. 
Example (QBio): orch 10K + 19 sub-agents 31K = 42K.
MA Total (Critical Path)
Orchestrator + SUM(fan_out)max(single sub-agent within fan_out) total tokens. Only the slowest parallel sub-agent counts. This determines how long the user waits. 
Example (QBio): orch 150K + max(19 sub-agents) 90K = 240K. The other 18 sub-agents (28K-67K each) finished earlier and don't add to wait time.
MA Out (Critical Path)
Orchestrator output + SUM(fan_out)max(single worker within fan_out). Output tokens along the latency-determining path. 
Example (QBio): orch output 10K + max sub-agent output 4K = 14K.
SA/MA cost
SA Total / MA Total. Example (QBio): 1.6M / 1.1M = 1.4x (MA is 1.4x cheaper).
SA/MA latency
SA Total / MA Total (Critical Path). Example (QBio): 1.6M / 240K = 6.5x (MA is 6.5x faster).

Issue 1 — MA token counts in result.json are orchestrator-only (sub-agents omitted)
Status: reproduced against the raw trajectories of all 5 pilot samples.
Scope: Harness-wide — affects every multi-agent (MA) run.

Issue 2 — Verifiers that credit shape over substance (understate the SA→MA gap)
Status: 3 of 5 pilot samples. Scope: task-authoring / verifier quality (recurs across samples). Severity: High — the pilot's defining weakness: it turns genuinely good tasks into sub-bar "Borderline" results and leaves some rewards reward-hackable.
What happens. The reward that survives to training does not measure the actual task. Two flavors:
* Fully structure-only (EMERG, COUNTY): verify.py checks only shape — row counts, column headers, JSON keys, chart presence, keyword-prefix, string length, format regex — never whether values are correct. A well-formed but hollow/fabricated output scores high, so SA banks undeserved credit and the measured gap is only a floor.
* Substance but mis-weighted (COFC): a real answer-key verifier, but a 20% structural floor + a few greppable fields (case_name / judge / word_count) let a non-reading SA bank ~0.59, compressing a real 30.5 pp correctness gap into a sub-bar 23.8 pp.


Evidence.
* EMERG — SA's fabricated rows (invented UEIs) score; its 9 honest "unable to confirm" hedges score 0.
* COUNTY — a 74-row garbage sheet would score 1.0; SA's ~10-of-21-defaulted rows still bank 0.79 (the §2.8 exemplar).
* COFC — a 0.19 structural floor + greppable fields float SA to 0.587; the correctness-only gap is already 30.5 pp.


Impact. Two of the three Borderline verdicts (COUNTY; COFC near-miss) are verifier artifacts, not bad tasks; EMERG is "provisional" for the same reason. Trained on these rewards as-is, a model learns "produce well-shaped output," not "do the task" — a reward-hacking / degeneration risk.


Recommended fix. Require at least one semantic/rubric check per task (authorable from instruction.md without a full oracle): resolve cited URLs, validate IDs against a frozen snapshot, spot-check values/verdicts, grade coverage against ground truth. Reweight/gate structural credit on a minimum correctness floor, and raise granularity toward ≥10 components. (This is the fix Turing already shipped in the later deliveries — Batch 16 & 47 are 63/63 substance — so it is validated.) In short: every grader should combine substance + structure checks — never structure-only.
Issue 3 — SA scores run high — a verifier-inflation side-effect (low standalone concern)
Status: 4 of 5 samples run SA high (0.44–0.79); only COMMUNITY (0.21) is genuinely low. Scope: task difficulty + verifier calibration. Severity: Low (standalone) — the gap, not the SA level, is what we grade.


What happens. We do not target any particular SA level — the SA→MA gap is what we grade, not the SA score. For context, SA sits at 0.44 (ECON), 0.55 (EMERG), 0.59 (COFC), 0.79 (COUNTY) — only COMMUNITY (0.21) is low. Two drivers: (a) verifier-inflation (see Issue 2) — weak/mis-weighted verifiers credit hollow SA output (EMERG, COUNTY, COFC); (b) scriptable backbone — some tasks have a greppable/numeric spine SA can partially solve without real reading.


Impact. These high SA scores are largely verifier-inflated (Issue 2), not evidence the tasks are easy. Our operative standard is the relaxed gap-based bar; we do not gate on or target the absolute SA level. Where high SA hides a real gap, the fix is the verifier (Issue 2), not the task; only where SA rides a scriptable backbone is there a genuine task-design action. This is the same "raise SA difficulty" framing as the Batch-16 near-miss cluster — but here it is verifier calibration, not an SA-score target.
Recommended fix. (1) Fix the verifiers (Issue 2) — that alone widens the measured gap for EMERG/COUNTY/COFC; (2) where a task has a scriptable/greppable backbone, make sub-tasks harder or less greppable so SA can't partial-credit its way up; (3) run ≥3 SA trials on razor-thin cases, since single-trial noise can flip a verdict.
Issue 4 — Declared-vs-realized topology & taxonomy mislabels (metadata)
Status: spans multiple samples. Scope: metadata / labeling (task-authoring). Severity: Low — cosmetic, but it distorts pattern/domain-coverage accounting.
What happens.
* Topology: ECON declared Hierarchical but executed as a flat fan-out (depth-2) — 37 co-equal writers, one incidental depth-3 spawn; COMMUNITY under-declared dag_depth (2 declared vs depth-3 observed). So "Hierarchical" tags don't always match the realized spawn tree.
* Domain / dir-slug: ECON is filed as CREATIVEVIZ / SLIDES but is knowledge-research / long-writing (a prose .docx); COUNTY's dir-slug (…-CODESWE-COUNTY-SERVICE-DEPENDENCY-SWEEP) vs the actual canada-ca GC-Digital-Standards audit. In both, task.toml is correct — the dir slug is the mislabel.


Impact. If pattern/domain coverage is tracked from declared labels, the tranche looks like it has more genuine Hierarchical and more creative-viz / code-swe coverage than it actually does. Pure accounting — no reward effect.
Recommended fix. Relabel to the realized pattern (e.g. Fan-out→Synthesize for ECON) or design tasks that force real delegation depth; fix dir slugs to match task.toml; reconcile dag_depth with the observed spawn tree. (task.toml content is generally accurate — align the slugs/labels to it.)
Issue 5 — Standardize verifier / judge naming & script format
Status: observed across the pilot. Scope: tooling / process consistency. Severity: Low (hygiene).
What happens. Grader files and conventions vary sample to sample — some tasks grade with verify.py (deterministic rules), others with judge.py (LLM), and filenames, entrypoints, and reward-output paths are not uniform. That makes batch-grading, tooling, and review harder and more error-prone.
Recommended fix. Adopt one convention across the tranche: a fixed grader filename/entrypoint scheme (e.g. verify.py for deterministic, judge.py for LLM, both invoked via a standard test.sh), a consistent reward-output path (reward.txt / reward.json), and a documented interface — not per-author variation.
Issue 6 — Grade every produced artifact, not just the primary deliverable (extends Issue 2)
Status: confirmed on COMMUNITY (reels). Scope: verifier coverage. Severity: High wherever an ungraded artifact carries reward weight.


What happens. Even when the main grader is substance-based, the secondary artifacts a task requires (videos/reels, charts, slides, aux files) are often graded structure-only — so they can be well-formed but content-empty and still score full. Example — COMMUNITY: the 16 per-forum reels are 0.15 of the reward but graded only on duration / animation / OCR / manifest; SA scored 16/16 valid reels vs MA's 11/16 while its clustering recall was ~5%, so the video score is fully decoupled from task quality.


Recommended fix. Give every scored artifact its own content rubric, not just the primary deliverable — e.g. for a video, a text-based rubric that transcribes/OCRs it and grades what it conveys against the gold (correct clusters/counts); for charts, check the plotted values. (This is Issue 2 applied at per-artifact granularity.)

1. The near-miss cluster (7 borderlines, 23–28 pp)
Every borderline in this delivery is a genuine, substance-verified gap that lands just under the 30 pp bar because the SA baseline scores 60–75%. SA gets there by scraping partial credit on the scriptable / numeric / mechanical backbone of the task while collapsing on the hard reading-and-synthesis core — the exact behavior we want the swarm signal to reward. Two illustrative shapes:
* Equal sub-check weighting dilutes a large sub-gap. TRANSIT-TITLE-VI: SA nails the scriptable numeric backbone (0.84) which is weighted 0.30, banking a ~0.25 floor; its real failures (6/13 citations, 16/25 comments, 14/19 route narratives, a 10K report vs MA's 64K) get averaged down to a 24.2 pp gap. CLINICAL-TRIAL-RBM (24 pp) and TAXCOURT (which clears at 40.6 pp) show the same backbone effect.
* A high partial-credit floor on a hard task. CHANGE-HEALTHCARE-TABLETOP (24.6 pp) is a real 50-source, 9-deliverable task — SA still banks 0.69 on structurally-present-but-hollow output (19/30 sources, 0 valid inject-ID references).


Recommendation: raise SA difficulty, don't discard. For each near-miss the fix is to shrink SA's partial-credit floor — more sources under a tighter budget, and reweighting the hard reading/synthesis sub-checks above the mechanical backbone (TRANSIT-TITLE-VI and CLINICAL-TRIAL-RBM show SA banking ~0.25–0.30 on scriptable components while failing the reading core). 6 of the 12 declared-Hierarchical samples actually executed as depth-2 flat fan-out: the orchestrator spawned every worker directly, and because sub-tasks are typed explore (spawn-denied), no worker spawned a child, so the declared middle tier exists only as a file-based data dependency, not a real spawn tree.
