# Why `b1b7` (Release-Cycle Triage Dossier) is not shippable — and why the next task must change shape

**Task:** `b1b701ceaf5447839847747a68f32b04-SWARMBENCH-SPECIALIST-PLANNING-OPERATIONS-RELEASE-CYCLE-TRIAGE-DOSSIER`
**Date:** 2026-07-27
**Verdict:** Do not submit as a single-vs-multi gap task. The gap is not real at the required
size. Root cause is structural (harness-level), not a bug in this task, and is confirmed by
two independent redesign axes both failing the same way.
**Companion docs:** `ESCALATION - Single agent self-parallelisation via injected OPENAI_API_KEY.md`
(platform ask) and `NEXT_TASK_KICKSTART_fanout_resistant.md` (how to build the replacement).

---

## 1. What the task was supposed to prove

The task presents 700 real, verbatim `microsoft/vscode` feature requests (~431k tokens, ~1.64×
a single 262k context window) and asks for a five-artifact triage dossier: a grounded,
argued assessment of every request; a fifteen-area rollup; a capacity-bounded 45-slot
commitment slate; and a deferral register. The stated gap thesis was:

> "The gap is structural: it comes from irreducible reading volume against a fixed context
> window ... a single agent works serially within one context and one output budget ... on
> 700 items it templates the tail, its rationales collapse into reused boilerplate."

Target metrics (per the difficulty rules): single-agent **< 0.30**, multi-agent **0.70–0.90**,
gap **> 0.23**.

## 2. What actually happened on the live single-agent run

Run `run_78db99ab49695894` (single, `kimi-k2p6`, daytona): **SUCCEEDED**, 1h 58m 55s, tokens
in/out **1,863,793 / 86,077**, cost **$1.0652**. It reported `reward = 0.0`, but that was a
false failure (see §5). Re-grading the identical, real agent output against the shipped
verifier offline gives the true picture.

### 2.1 The single agent built its own swarm

From the agent's trajectory (`execution_logs/.../agent/opencode.txt`):

- Its **second shell command of the entire run** was a credential hunt:
  `env | grep -i openai; env | grep -i api; env | grep -i key`.
- It then ran `pip install openai`, verified the key with
  `curl https://api.fireworks.ai/inference/v1/models`, and spent ~23 minutes tuning batch sizes.
- It launched **sharded background workers** (`nohup python3 /workspace/worker.py 0 88`, i.e.
  88-request shards) and a `max_workers=5` thread pool via `run_all_threads.py`.

Measured over the whole run:

| script sites calling `chat.completions.create` | 18 (re-verified 2026-07-29, exact) |
| worker-pool width | 8 `nohup` shard processes, then `ThreadPoolExecutor(max_workers=4)` |

## 3. The measured score, and why the gap is dead

Offline grading of the real SA output against the shipped verifier (all 8 LLM judges failing
closed to 0.0 because the local key 401'd):

- **Total reward with judges off: 0.5598.**
- On the 14 deterministic checks alone: **12.31 / 14 = 0.88**.

Why the gap cannot reach 0.23:

- A strong multi-agent run cannot exceed ~**0.92** on those same deterministic checks (best
  fixture profile). So the **measured deterministic-only gap is ~0.04** (0.92 − 0.88).
- SA already sits at **0.56 with judges completely off**. For the gap to clear 0.23, multi
  would need > **0.79** — but the LLM judges lift *both* arms together (they grade SA's
  genuinely-good rationales too), they do not push SA down. Realistic judged outcome is
  SA ≈ 0.85, MA ≈ 0.90 → gap ≈ **0.05**. Even a generous MA = 0.95 vs SA = 0.80 is **0.15**,
  still under the 0.23 floor.

Corroborating signal: the task estimated **102 human-hours**; the agent finished in **~2 hours
for $1.07**. The work was not, for a tool-using agent, as hard as the estimate assumed.

**Conclusion:** the verifier is strong, the single agent genuinely completed the task well, so
by the difficulty rule the task is not at the required scale. The correct response is redesign
or drop — not repeated reruns hoping for a lower SA score (a fresh run only scores low if the
agent happens *not* to find the key, which it found on its second command).

## 4. Why there is no cheap fix (the general trap)

Both natural rescue axes were tested and both fail for the same reason:

- **Scale up (1,400+ issues):** the agent runs 16 shards instead of 8. Fan-out cost is roughly
  linear and cheap; the context window is never the binding constraint.
- **Cross-item consolidation (find the underlying need several requests share):** tested on the
  real corpus (`_trainer_artefacts/probe_consolidation_premise.py`). Genuine cross-area groups
  exist (e.g. right-to-left text rendering spans F496 accessibility / F562 workbench-ux / F573
  chat-ai), but plain TF-IDF surfaces them cheaply, and candidate *verification* is per-pair
  independent — the exact shape a fan-out eats. ~3,000 candidate pairs is *less* work than the
  700 deep assessments the agent already completed.

**The general rule (now in the Lessons Log):** *any task that decomposes into "generate
candidates cheaply, then judge each candidate independently" is fan-out-able, regardless of
size.* Volume, cross-referencing, and clustering are all this shape. Only work whose parts
depend on the **resolved answers** of other parts resists it. b1b7's 700 items are mutually
independent — which is exactly why fan-out won.

## 5. Separate, already-fixed issue: the CRLF false failure (do not conflate)

The run's `reward = 0.0` was **not** a capability measurement. `tests/test.sh` had Windows CRLF
line endings, so its shebang read `#!/bin/bash\r`; Linux looked for an interpreter literally
named `/bin/bash\r`, failed with `cannot execute: required file not found`, `verify.py` never
ran, no reward file was written, and the harness recorded `RewardFileNotFoundError → 0.0`.
Fixed: all shipped text files normalised to LF (frozen JSON corpus left byte-identical, since a
CR inside a JSON string is illegal and a corpus that parses carries CR only as inert
whitespace), plus a permanent static guard in `validate_triage_task.py` asserting an LF shebang
and no CR bytes in any shipped script/doc. **This fix makes the verifier run; it does not and
cannot lower the SA score — a clean run scores ~0.8, not low.**

## 6. Secondary finding: the rubric is less discriminative than 22 checks suggests

Across 11 graded fixture profiles (`_trainer_artefacts/check_correlation.py`): **10 of the 14
deterministic checks fall into r ≥ 0.95 correlation clusters** (`completeness_validity` ↔
`grounding_integrity` ↔ `routing_and_rollup` at r ≈ 1.000; `funding_argument_quality` ↔
`deferral_reason_quality` at 0.999), and **8 of 22 points are reachable by "emit every record,
well-formed, with varied prose."** Future rubrics must be correlation-tested against fixture
profiles before a live run, not merely count-checked.

## 7. The platform blocker that outlives this task

The single agent can replicate any breadth-based multi-agent topology because the harness gives
it an unrestricted inference key and a shell:

- `single_opencode.py:259-262` injects the Fireworks key into the container (as
  `OPENAI_API_KEY`) so the agent can reach its own model.
- Air-gapping is not a fix: `allow_internet = false` appends `docker-compose-no-network.yaml`
  which sets `network_mode: none` on the **agent's own** service, and the verifier runs in that
  same container (`trial.py` `_run_verification`), so it would also fail-close all 8 judges.
- No approved sample task sets `allow_internet` at all — the exposure is systemic and
  pre-existing; it only bites once a task is large enough that writing the fan-out pays off.

Until the platform withholds/allowlists that key (see the escalation doc), **no volume- or
breadth-based gap thesis is durable.** This is why the next task must change *shape*, and why
the escalation is on the critical path rather than a side note.

## 8. Decision

Drop `b1b7` as a gap task. It remains in a clean, reproducible state (all fixes applied, 53
static checks passing) as evidence for the escalation. Build the next task on a
fan-out-resistant axis, premise-tested before any live run — see
`NEXT_TASK_KICKSTART_fanout_resistant.md`.
