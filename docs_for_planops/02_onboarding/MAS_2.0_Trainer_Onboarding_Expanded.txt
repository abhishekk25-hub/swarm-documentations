WHAT THE PILOT EXPOSED
A package can be structurally
correct and substantively empty.
WHAT A SHALLOW CHECK CAN PROVE
The file exists.
The workbook has the expected sheets.
The JSON contains the required keys.
A chart or video was produced.≠WHAT THE TASK ACTUALLY NEEDS TO PROVE
The reported values are correct.
The cited evidence supports the conclusion.
All required sources were covered.
The final synthesis reflects the completed analysis.
This difference is the reward-hacking risk: a model
can learn to produce convincing shapes instead of
doing the task.

WRITING STRONGER MANIFEST ENTRIES
One entry should explain one
implemented check.
Too vague
"Checks whether the spreadsheet is correct."
Only a label
"Duplicate-row check."Mechanics
"Counts unique repo_name values and compares that count with total
rows; any difference means the submission contains duplicated
coverage."
Authenticity protection
"Prevents one researched repository from being copied repeatedly to
imitate a complete 74-repository audit."
The explanation must be detailed enough for a reviewer to understand the check
without opening verify.py, while check_function proves that the described logic is
actually implemented.

PILOT VERIFIER EXAMPLE / 1 OF 4
EMERG: confidence was rewarded
over truth
01
SELECTED TASK EXAMPLEWhat happened: the verifier recognized valid-looking prefixes, formats, and
populated fields. Fabricated identifiers and confident verdicts could therefore earn
credit, while an honest "unable to confirm" response earned none.
Why that is harmful: the reward teaches the model that sounding certain is more
valuable than being grounded. This is the opposite of the behavior expected in
procurement review.
Better pattern: verify identifiers against a trusted source, resolve cited URLs, spot-
check verdicts against authority, and recognize justified uncertainty as a valid
outcome.
Expected effect: fabricated certainty loses credit; supported findings and transparent uncertainty become the
rewarded behavior.

COUNTY: completeness was
mistaken for correctness
02
SELECTED TASK EXAMPLEWhat happened: row count, headers, JSON shape, and chart presence showed that
a package was complete, but they did not prove that the 74 repository audit values
were correct.
Why that is harmful: a workbook filled with defaults or placeholders can look
production-ready and still earn a high reward. The measured score then overstates
the work actually completed.
Better pattern: keep the delivery checks, then add known-correct spot checks for
selected repositories and limited semantic review for claims that cannot be tested
with simple equality.
Expected effect: a complete but hollow workbook fails the substantive checks, while a grounded audit receives
credit even without a full oracle.

A REUSABLE REWARD-DESIGN METHOD
Design checks from the task's
evidence, not from a fixed formula.
1Name the decisions that make
the task valuable.2Identify the source evidence that
can prove each decision.
3Choose an exact, semantic, or
combined check for each rule.4Run SA and MA, then inspect
which checks separate real work
from formatting.# COFC example: task-specific evidence checks
if quote_appears_verbatim (opinion, row.quote):
    credit("grounded legal evidence")
if row.outcome == held_out.outcome :
    credit("actual court ruling")
if docket_matches (row.docket, held_out.docket):
    credit("correct case identity")
These checks are correct for a legal-opinion task. A bridge, video, code, or planning
task needs different evidence checks. The reusable pattern is task outcome →
proof → check, not one universal weight setting.

WEIGHTING EXPLANATION / 1 OF 3
Why high structural weight is risky
01
SELECTED WEIGHTING NOTEStructure confirms that an artifact can be opened and consumed. It does not confirm
that the analysis inside it is correct. If structure carries a large guaranteed share, a
model can earn meaningful reward before reading the sources or making the required
decisions.
COUNTY example: 74 rows with the right headers could appear complete even when many
audit values were defaults or placeholders.

WEIGHTING EXPLANATION / 2 OF 3
Why every check declares weight 1
02
SELECTED WEIGHTING NOTEPhase 2.1 uses equal point values so a trainer cannot create a large guaranteed floor
for easy structural checks. The reward becomes the share of individually implemented
checks the output actually satisfies.
The supplied COUNTY verifier averages ten components: four static checks, four

How to make equal points

03
SELECTED WEIGHTING NOTEEqual points do not make the rubric shallow. Trainers control what the reward

FAIR FAILURE
Low SA is useful only when the task
caused it.
VALID CAPABILITY FAILURE
Missed evidence across a large corpus.
Inconsistent reconciliation across sources.
Context pressure caused coverage loss.
Final synthesis omitted independent findings.INVALID ARTIFICIAL FAILURE
Missing browser or required tool.
Wrong output path or inaccessible input.
Unfair timeout or context difference.
Hidden requirement or verifier crash.
A single-digit score is not the goal by itself. A
genuine, explainable single-agent limitation is the
goal.

TRAINER WORKFLOW / STEP 1 OF 8
Choose a scenario with real
coordination pressure
01
SELECTED WORKFLOW STEPStart with a plausible user and a difficult decision. Use recent, less-canonical books,
presentations, reports, or datasets that the base model is unlikely to have memorized.
The work should require reading supplied evidence and reconciling independent
evidence units, not repeated busywork or recall from pretraining.
Example: prioritize 160 county bridges using a current supplied inventory, recent
hazard records, declarations, and gage evidence rather than a famous textbook case
the model may already know.
